# دليل تشغيل وتسليم AlTayerERP

## هدف الحزمة

يوثق هذا الدليل مسار تحقق قابل للإعادة قبل تسليم النظام. وهو لا ينشر خدمة، ولا يغير `master`، ولا ينفذ ترحيلاً أو بيانات على قاعدة الإنتاج. تستند الحزمة إلى نجاح **19 من 19** اختبار خادم محلي، وبناء API وسطح المكتب في وضع `Release` مع تحويل التحذيرات إلى أخطاء.

| النطاق | أداة التحقق | الغاية |
|---|---|---|
| Linux أو CI | `scripts/verify-release.sh` | بناء API وسطح المكتب المتقاطع، تشغيل اختبارات الخادم، وفحص عقود منع التكرار. |
| Windows | `scripts/Verify-Release.ps1` | بناء API وWinForms وMAUI Android وتشغيل الاختبارات من بيئة الإصدار الفعلية. |
| MySQL التجريبية | قائمة القبول أدناه | تطبيق ترحيل السجل واختبار القيد الفريد والتزامن، من دون استخدام الإنتاج. |
| هاتف فعلي | قائمة القبول أدناه | التحقق من الاتصال بالشبكة الداخلية وتدفقات المستخدم من الطرف إلى الطرف. |

> لا يصبح الإصدار مقبولاً للإنتاج إلا إذا اكتملت عناصر القبول جميعاً. نتائج البناء المحلي تثبت جودة الكود القابل للفحص، ولا تعوض اختبار الشبكة أو MySQL أو الجهاز الفعلي. يجب تسجيل اسم بيئة الاختبار وتاريخ التنفيذ ونتيجة كل سيناريو في محضر القبول قبل اعتماد أي نشر.

## المتطلبات قبل البدء

ينبغي أن تكون نسخة العمل في الفرع `agent/unified-phase1-screens`، وأن تكون قاعدة الاختبار نسخة معزولة قابلة للاسترجاع. يلزم Windows 10/11 مع Visual Studio و.NET SDK 8 و10 وحمولة MAUI Android وAndroid SDK عند التحقق من تطبيق MAUI. يجب ألّا تشير أي متغيرات بيئية أو إعدادات اتصال في جلسة الاختبار إلى قاعدة الإنتاج.

## تسلسل التحقق

### 1. التحقق البرمجي

شغّل في Linux أو بيئة CI:

```bash
bash scripts/verify-release.sh
```

وعلى Windows شغّل PowerShell من جذر المستودع:

```powershell
.\scripts\Verify-Release.ps1
```

يجب أن ينجح البناء والاختبارات بلا تحذيرات. أي فشل يوقف التسليم ولا يعالج مباشرة في قاعدة البيانات.

### 2. ترحيل قاعدة اختبار MySQL

راجع أولاً الملف `Database/Scripts/20260820_add_idempotency_records.sql`، أو استخدم ترحيل EF `20260820043000_AddIdempotencyRecords` بعد أخذ نسخة احتياطية من قاعدة الاختبار. بعد التنفيذ تحقق من وجود `idempotency_records` والفهرس `UQ_Idempotency_Record_Scope_Key`. لا تنفذ ذلك تلقائياً على الإنتاج.

### 3. قبول منع التكرار

| السيناريو | الإجراء | النتيجة المقبولة |
|---|---|---|
| سند قبض مع إعادة إرسال | أرسل الطلب مرتين بالرأس نفسه `Idempotency-Key` وبالحمولة نفسها | يعاد نفس `voucher_ID` و`voucher_No` ولا ينشأ مستند ثانٍ. |
| طلب صرف مع إعادة إرسال | أرسل الطلب مرتين بالرأس نفسه وبالحمولة نفسها | يعاد نفس `request_ID` و`request_No` ولا ينشأ طلب ثانٍ. |
| مفتاح مع حمولة مختلفة | غيّر المبلغ أو أحد البنود وأعد استخدام المفتاح | `409 Conflict` ولا ينشأ أي مستند أو طلب جديد. |
| قراران متزامنان | استخدم مستخدمين مختلفين على طلب اعتماد واحد | يقبل أول انتقال صحيح فقط، وتسجل المحاولة الأخرى بالنتيجة المتوقعة من حالة الطلب. إذا لم يتحقق ذلك، يوقف الإصدار ويُسجل عيب تزامن قبل النشر. |

### 4. قبول سطح المكتب والجوال

يختبر مستخدمان مختلفان على شبكة API الداخلية هذه السلسلة: تسجيل الدخول، اختيار الشركة والفرع والسنة، إنشاء طلب صرف، إرساله، ظهوره في مركز الاعتماد، اتخاذ قرار من مستخدم غير المنشئ، إنشاء سند قبض، ثم إعادة محاولة حفظ السند وطلب الصرف بعد قطع اتصال مصطنع. يفحص المستخدم الرسائل الظاهرة للتأكد من عدم إظهار استجابة HTTP خامة أو تفاصيل اتصال/قاعدة بيانات.

## قرار النشر والتراجع

يتخذ قرار النشر فقط بعد حفظ لقطات نتائج البناء، ونتيجة اختبار MySQL، ونتيجة اختبار الجهاز. إذا أخفق ترحيل الاختبار أو ظهر تكرار، يوقف الإصدار، وتسترجع قاعدة الاختبار من النسخة الاحتياطية، ويعاد تقييم الإصلاح في الفرع نفسه. لا يستلزم هذا الدليل ولا يسمح بتشغيل `git merge` إلى `master`.
