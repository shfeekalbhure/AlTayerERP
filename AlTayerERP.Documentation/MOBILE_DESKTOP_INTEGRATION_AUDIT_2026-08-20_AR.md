# تقرير التدقيق التكاملـي — تطبيق الجوال وسطح المكتب

**المستودع:** `shfeekalbhure/AlTayerERP`  
**الفرع:** `agent/unified-phase1-screens`  
**التاريخ:** 20-08-2026  
**النطاق:** تطبيق الجوال MAUI، تطبيق سطح المكتب WinForms، وواجهات API الخاصة بالحفظ والجلسة والسندات وطلبات الصرف.

## الحكم التنفيذي

توجد طبقة API مشتركة للحفظ والصلاحيات ونطاق الشركة/الفرع/السنة، وتطبيق الجوال وسطح المكتب يستعملانها في المسارات المالية الأساسية. قبل هذا التدقيق كانت هناك فجوتان مؤكدتان في مسار الجوال: تعديل السند لا يحمل رمز التزامن، واستجابات HTTP المهمة تفقد رمز الحالة عند تحويلها إلى رسالة. تم إغلاقهما في التحديث `bd9435b`.

لا يُعد تطبيق الجوال **Offline-First** بعد؛ فهو يحفظ الجلسة وإعداد الاتصال فقط، ولا يملك مخزن بيانات تشغيليًا محليًا أو قائمة مزامنة. هذه فجوة تنفيذية مستقلة لا يعالجها تعديل صغير.

## العيوب المؤكدة التي أُغلقت

| المعرف | العيب | الأثر | المعالجة |
|---|---|---|---|
| F-01 | قوس زائد في `VoucherEntryService.cs` | منع بناء تطبيق الجوال بخطأ `CS1022` | حذف القوس الزائد في `d2eb17c` |
| F-02 | واجهات تفاصيل سندي القبض والصرف لا تعيد `RowVersion` | يمكن لتعديل جوال متأخر أن يكتب فوق تعديل أحدث | API يعيد `rowVersion`، وDTO والواجهة يعيدان إرساله عند الحفظ |
| F-03 | مسار تعديل السند يعيد تعارض التزامن كـ `400` | لا يستطيع العميل تمييز التعارض عن خطأ بيانات | إعادة التعارض المعروف كـ `409 Conflict` |
| F-04 | عدة خدمات جوال تحوّل `401/403/409` إلى `InvalidOperationException` بلا حالة HTTP | لا يمسح التطبيق جلسة منتهية بصورة موحّدة ولا يميّز التعارض | `MobileApiException` يحتفظ بحالة HTTP والرسالة الآمنة؛ طبّق على السندات وطلبات الصرف والاعتمادات |
| F-05 | اختلاف مكرر في تحويل أخطاء JSON بين خدمات الجوال | رسائل غير متسقة وخطر فقد معنى الخطأ | استخدام منشئ خطأ مركزي في المسارات التي عُدلت |

## ما طابقناه

1. **الحفظ:** إنشاء/تعديل سند الجوال يصل إلى `api/FinancialVoucher` نفسها التي يستخدمها سطح المكتب، والخادم يفرض الفرع والسنة والمستخدم من الجلسة بدل قبولها من العميل.
2. **النطاق والصلاحيات:** واجهات الجوال للسندات وطلبات الصرف تستخرج `ServerSession`، وتتحقق من صلاحية الشاشة ونطاق الفرع والسنة قبل قراءة أو تعديل البيانات.
3. **التكرار:** إنشاء السند وطلب الصرف من الجوال يرسلان `Idempotency-Key`، والخادم يملك سجل idempotency لمعالجة إعادة الإرسال.
4. **الجلسة:** الجوال يخزن الرموز في `SecureStorage` ويجددها، وسطح المكتب يحتفظ بها في الذاكرة ويجددها قبل انتهاء الرمز من شاشة التشغيل الرئيسية.
5. **الربط:** كلا التطبيقين يستخدمان API واحدًا، لكن إعداد الاتصال مختلف: سطح المكتب من `ALTAYER_API_BASE_URL` والجوال من إعداد USB/Wi-Fi المحفوظ في `Preferences`.

## الفجوات المتبقية

| الأولوية | الفجوة | سبب عدم إغلاقها ضمن هذا التحديث | الإجراء التالي المطلوب |
|---|---|---|---|
| عالية | لا توجد قاعدة SQLite/Outbox في تطبيق الجوال | لا توجد بنية بيانات محلية أو عقود مزامنة أو قواعد تعارض مُعتمدة | تنفيذ موجة Offline مستقلة: مخزن مرجعي، Outbox مشفر، مفاتيح idempotency ثابتة، مزامنة واسترجاع تعارض |
| عالية | لا توجد اختبارات تكامل تشغيلية مرئية للجوال مع API وقاعدة بيانات | بيئة التدقيق لا تحتوي `dotnet` أو قاعدة تشغيل للمشروع | تشغيل CI يبني الحل ويختبر: تسجيل الدخول، إنشاء/تعديل/تعارض سند، انتهاء الجلسة، وطلب الصرف |
| متوسطة | خدمات جوال ثانوية ما زالت تستعمل معالجات خطأ محلية | التوحيد بدأ بالمسارات المالية الحرجة، ولا ينبغي تغيير كل الشاشة بلا اختبار | نقل خدمات المرفقات والتقارير والبحث تدريجيًا إلى `MobileApiErrorHandler.CreateException` |
| متوسطة | إعداد الاتصال ليس عقدًا موحدًا بين التطبيقين | لكل عميل مصدر إعداد مختلف | إضافة ملف إعداد تشغيل موثق/موزع أو endpoint إعداد موثوق؛ لا تضع أسرارًا في التطبيق |
| متوسطة | تفاصيل السند المعاد تحميلها تعرض بيانات محاسبية كاملة، لكن لا توجد شاشة توحيد صريحة لسياسة المرفقات والطباعة بين الجوال والدسكتوب | اختلاف واجهات الاستخدام وليس خطأ حفظ مباشر | اعتماد عقد عرض موحد للمرفقات والطباعة وتغطية قبول مشتركة |

## شروط الإغلاق التالية

لا تُعلن جاهزية كاملة قبل نجاح اختبارات قبول فعلية على فرع نظيف تشمل:

1. إنشاء سند من الجوال ثم فتحه وتعديله من سطح المكتب.
2. فتح السند نفسه في جهازين، تعديل الأول، ثم تحقق أن الثاني يتلقى `409` ولا يفقد بيانات الأول.
3. انتهاء Access Token أثناء الحفظ، ثم تجديد الجلسة أو العودة الآمنة لتسجيل الدخول.
4. إعادة إرسال طلب حفظ بعد انقطاع الشبكة والتأكد من عدم تكرار السند أو طلب الصرف.
5. اختبار صلاحيات مستخدم محدود على الجوال وسطح المكتب للفرع والسنة نفسيهما.
