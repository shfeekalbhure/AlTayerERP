## نتيجة خط الأساس

تم تثبيت .NET SDK 8 لتشغيل مشاريع الخادم والاختبارات، ثم شغّل الأمر التالي بنجاح:

```bash
dotnet test AlTayerERP.Tests/AlTayerERP.Tests.csproj -c Release
```

كانت النتيجة الابتدائية **19 اختباراً ناجحاً من 19** بلا اختبار متجاوز أو فاشل. وبعد تدقيق طبقات الخادم والعملاء وإضافة اختبارات الانحدار، كانت نتيجة التحقق الأخيرة عبر `scripts/verify-release.sh` هي **58 اختباراً ناجحاً من 58** بلا اختبار متجاوز أو فاشل. يغطي ذلك صحة استجابة الخادم، قواعد منع ترحيل السند، تحقق حقول السند، منع التكرار المالي، تسلسل حجز الأرقام، القرارات المتزامنة للاعتماد، تدوير Refresh Token، معالجة الاستثناءات الآمنة، وعقود عرض الخطأ والجلسة في MAUI وسطح المكتب، وعقد العرض المختصر للسند، وتزامن تعديل طلبات الصرف، وسجل قرارات الاعتماد، ورموز التزامن للسندات، وأمن مرفقاتها، وسياسة HTTPS، وبوابة CI.

> نجاح اختبارات SQLite يثبت صحة القيود العلائقية في طبقة EF، لكنه لا يغني عن اختبار التزامن والأقفال والترحيل على MySQL في بيئة اختبار معزولة.

## فحوصات إلزامية قبل القبول النهائي

يجب تنفيذ هذه الخطوات في جهاز Windows مع Visual Studio و.NET SDK/Workloads المطابقة قبل إصدار حزمة سطح المكتب أو Android:

1. بناء `AlTayerERP.sln` بوضع `Release` ثم تشغيل `dotnet test AlTayerERP.Tests/AlTayerERP.Tests.csproj -c Release`.
2. بناء `AlTayerERP.Mobile.Office` بوضع `Release` مع Android SDK، وتثبيت APK على جهاز ضمن شبكة الخادم الداخلية.
3. تطبيق ترحيل `20260820043000_AddIdempotencyRecords` أولاً على نسخة MySQL تجريبية ثم اختبار مفتاح `Idempotency-Key` المتكرر والمتعارض لسند القبض وطلب الصرف.
4. تطبيق `20260821000000_AddPaymentRequestRowVersion` أو السكربت المكافئ على MySQL تجريبي، ثم تنفيذ تعديلين متزامنين لطلب صرف بالرمز نفسه والتحقق من `409 Conflict` للكاتب المتأخر.
5. إجراء اختبار قبول يدوي كامل: دخول، شركة وفرع وسنة، طلب صرف وإرساله، ظهوره في الاعتماد، قرار مستخدم مختلف، قراءة سجل القرار، إنشاء سند قبض، وإعادة المحاولة بعد قطع شبكة مصطنع.

لا يمنح هذا التقرير قبولاً نهائياً للإنتاج قبل تنفيذ الخطوات السابقة؛ لكنه يثبت أن طبقة الخادم والاختبارات القابلة للتشغيل في البيئة الحالية اجتازت خط الأساس.
