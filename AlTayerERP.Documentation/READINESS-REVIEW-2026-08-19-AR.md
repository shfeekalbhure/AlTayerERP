# تقرير مراجعة وتجهيز مشروع AlTayerERP

**تاريخ المراجعة:** 19 أغسطس 2026

**الفرع:** `chore/prepare-unified-phase1-screens`، مبني على `agent/unified-phase1-screens`

**النطاق:** مراجعة خط الأساس الموجود في `master`، إصلاح بوابات الأمان والجودة ذات الأولوية، وإضافة تحقق قابل للتكرار.

## الملخص التنفيذي

تم تجهيز خط أساس أفضل للمشروع من الناحية الأمنية وقابلية التحقق. أزيل نص الاتصال الذي يحتوي بيانات اعتماد من `appsettings.json`، وأصبحت سياسة CORS مغلقة افتراضيًا ولا تسمح إلا بالأصول المعرفة في الإعدادات. أضيف ملف إعداد نموذجي ودليل عربي للتشغيل الآمن، كما أضيف مشروع اختبارات يثبت ثلاث قواعد أساسية في خدمة التحقق من السندات واختبارين إضافيين لحارس ترحيل السندات.

نجح بناء API والطبقات التابعة له، ونجحت الاختبارات الآلية الستة محليًا باستخدام **.NET 8 SDK 8.0.130**. كما نجح بناء Windows Forms وMobile Android على عوامل GitHub Actions المخصصة؛ أما بناء Windows Forms وAndroid محليًا فيحتاج بيئة Windows مع أدوات Desktop وMAUI Android.

| تشغيل API ضد MySQL | غير منفذ | يتطلب قاعدة بيانات وبيانات اعتماد يوفرها مالك البيئة |

## الملفات المهمة

يجب ضبط الاتصال من خلال User Secrets أو متغير `ConnectionStrings__DefaultConnection` كما هو موضح في [دليل الأمان والتجهيز](SECURITY-AND-SETUP-AR.md). لا ينبغي إعادة إضافة كلمة مرور إلى `appsettings.json` أو إلى أي ملف متتبع.

ينفذ التحقق الآلي من خلال [ملف GitHub Actions](../.github/workflows/ci.yml)، بينما توجد اختبارات قواعد السندات وحارس الترحيل في مشروع `AlTayerERP.Tests`. يجب تشغيل عامل Windows قبل اعتماد جاهزية تطبيق سطح المكتب، كما يجب تشغيل فحص `/api/health` بعد توفير MySQL فعلي.

## المتابعة اللاحقة

تمت مراجعة طلبات الدمج المفتوحة وتوثيق قراراتها في [تقرير فرز طلبات الدمج](OPEN-PR-TRIAGE-AR.md). كما تمت إضافة [دليل قاعدة البيانات](../Database/README_AR.md) الذي يوضح أن خط الأساس الحالي يجمع بين SQL يدوي وEF Core Migration جزئية، ولذلك لا ينبغي تشغيل الترحيلات تلقائيًا أو دمج حزم Phase1 الكبيرة قبل اعتماد مخطط واحد.

كشف التدقيق وجود تعريفات مكررة لبعض جداول المرحلة الأولى بين ملف التوافق والملفات المنفصلة. لم تُحذف الملفات التاريخية، بل تم توثيق ترتيب الاستخدام والتحقق المطلوب لتجنب إعادة تطبيقها على قاعدة قائمة. أضيفت سياسة صريحة في ملفات المشروع للتعامل مع تحذيرات Designer المولدة (`CS0169` و`CS0649`) وتحذيرات ربط XAML الاختيارية (`XC0022`) كملاحظات جودة غير مانعة، مع إبقاء أخطاء الكود الفعلية ظاهرة وفاشلة في CI.

بعد تشغيل تحقق إضافي، تم تصحيح using مكرر في `NumberGeneratorService` ومعالجة nullable في `ChartOfAccountsController` و`SystemSettingsController` و`FinancialVoucherController`، كما أزيلت منشئات الجلسة القديمة من وحدتي الشركات ومجموعات المستأجرين. أصبح بناء API الآن ناجحًا بصفر تحذيرات وصفر أخطاء، ونجحت الاختبارات الستة محليًا. أضيف اختبار مباشر لحارس الترحيل يثبت رفض السند غير الموجود وتمرير الطلبات غير المستهدفة، ثم نجحت فحوصات CI الستة على الالتزام `37d69b5`.

## العناصر المتبقية قبل الإنتاج

هذه الحزمة لا تعني أن النظام أصبح إصدارًا إنتاجيًا كاملًا. ما زالت هناك حاجة إلى تشغيل اختبارات قبول كاملة للدخول والصلاحيات والتهيئة ودورة السند من الإنشاء حتى الترحيل وإلغاء الترحيل، وإضافة اختبارات تكامل على قاعدة MySQL نظيفة، وتوحيد سياسة Migrations وملفات SQL، وفرز طلبات الدمج المفتوحة وربطها بإصدارات محددة.

كما يجب **تدوير كلمة المرور القديمة** إذا كانت مستخدمة فعليًا في أي بيئة، لأن إزالة القيمة من الملف الحالي لا تحذفها من تاريخ Git. ويجب تنفيذ مراجعة مستقلة للصلاحيات وسجل التدقيق قبل النشر الخارجي.
