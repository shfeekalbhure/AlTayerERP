# تقرير فريق كبار المستشارين: مشكلة عدم ظهور الشركات في AlTayerERP

**المشروع:** AlTayerERP  
**النطاق:** شاشة دخول `Mobile.Office` وقائمة اختيار الشركة  
**الفرع:** `agent/unified-phase1-screens`  
**خط الأساس:** `c0af898`  
**الحالة:** تم تنفيذ إصلاح الكود على الفرع، مع بقاء اختبار التكامل بقاعدة MySQL الفعلية مطلوبًا.

## 1. تشكيل فريق المراجعة

| الدور الاستشاري | نطاق الفحص | النتيجة |
|---|---|---|
| مستشار معماري | تتبع مصدر البيانات وحدود المسؤولية بين العميل وAPI وقاعدة البيانات | الجوال لا يتصل بقاعدة MySQL مباشرة؛ كل الطلبات تمر عبر API. |
| مستشار API و.NET | مراجعة المسارات العامة ومسار تسجيل الدخول وعقود JSON | وُجد مساران لقائمة الشركات بعقدين وشروط تصفية مختلفين. |
| مستشار MAUI | فحص `MainPage` و`Picker` و`AuthenticationService` والربط المرئي | شاشة الجوال كانت تستدعي المسار العام بدل المسار المخصص للدخول. |
| مستشار قواعد بيانات | تحليل شروط الشركة والمجموعة التجارية | ظهور الشركة في شاشة الدخول يتطلب شركة نشطة ومجموعة نشطة و`Show_In_Login = 1`. |
| مستشار أمن وصلاحيات | التحقق من عدم توسيع نطاق الدخول للمستخدمين | تم الإبقاء على قيد المجموعة وقيد الفرع للمستخدم غير مدير النظام. |
| مستشار جودة وإصدار | مراجعة الفرق، الفحص الساكن، وخطة الاختبار | `git diff --check` ناجح؛ تعذر `build/test` لأن .NET SDK غير مثبت في بيئة التنفيذ. |

## 2. السبب الجذري

كان عميل `Mobile.Office` يستدعي:

```text
GET api/Branches/GetCompaniesLookup
```

بينما يعرّف الخادم مسارًا مخصصًا لشاشة الدخول:

```text
GET api/Auth/LoginCompanies
```

المساران ليسا متكافئين. المسار المخصص للدخول يربط الشركات بالمجموعات التجارية ويطبق شروط `Company.Is_Active`, و`Group.Is_Active`, و`Group.Show_In_Login`. كذلك كان عقد الاستجابة في المسار المخصص يستخدم `Company_Name`، في حين أن DTO الجوال كان يعتمد أساسًا على `Company_Name_AR`. هذا التعارض كان يجعل مصدر البيانات وسلوك التصفية وعقد العرض غير موحدين، ويجعل تشخيص القائمة الفارغة مضللًا.

> **النتيجة العملية:** المشكلة ليست في عنصر `Picker` نفسه؛ بل في اختيار مسار API غير مخصص للدخول مع وجود عقدين مختلفين، إضافة إلى اعتماد ظهور الشركة على إعداد المجموعة التجارية.

## 4. شرط البيانات الذي يجب فحصه

حتى بعد الإصلاح البرمجي، لن تظهر الشركة في شاشة دخول الجوال إلا إذا تحققت الشروط التالية في قاعدة البيانات:

| العنصر | الشرط |
|---|---|
| الشركة | `companies.Is_Active = 1` |
| الربط | `companies.Group_ID` يطابق `tenant_groups.Group_ID` |
| المجموعة | `tenant_groups.Is_Active = 1` |
| السماح بالظهور | `tenant_groups.Show_In_Login = 1` |

أُضيف ملف تشخيص للقراءة فقط في `Database/Scripts/20260819_diagnose_mobile_login_companies.sql`. لا ينفذ الملف أي تعديل تلقائي. إذا أظهر أن `Show_In_Login` غير مفعّل، يجب اعتماد التعديل من مسؤول النظام ثم تفعيل الخيار من شاشة إدارة المجموعات التجارية أو تنفيذ التعديل المصرح به على السجل الصحيح.

## 5. التحقق المنفذ

تم تثبيت خط الأساس على الفرع الإلزامي، وفحص حالة المستودع قبل التعديل، ثم راجعت أدوار API وقاعدة البيانات وMAUI والاتصال والأمن. كما تم تنفيذ `git diff --check` دون أخطاء، وفحصت مراجع المسار والعقد بعد التعديل.

لم يمكن تشغيل `dotnet restore` أو `dotnet build` أو `dotnet test` لأن أمر `dotnet` غير مثبت في بيئة التنفيذ الحالية. لذلك لا أصف الإصلاح بأنه اجتاز اختبار بناء كامل حتى يُنفذ البناء على جهاز التطوير أو CI يحتوي على .NET 8 SDK وبيئة MAUI المناسبة.

## 6. خطوات الإغلاق المطلوبة على بيئة التشغيل

أولًا، شغّل API على نفس قاعدة البيانات التي يستخدمها الجوال، وتحقق من `GET /api/health`. ثانيًا، نفّذ استعلام التشخيص المرفق واقرأ قيمة `Login_Visibility_Status`. ثالثًا، إذا كان السبب إعدادًا، فعّل الشركة والمجموعة وخيار الظهور عند الدخول دون تغيير صلاحيات المستخدمين. رابعًا، أعد بناء API وتطبيق `Mobile.Office` ثم افتح شاشة الدخول وتحقق من ظهور الاسم العربي ومعرّف الشركة. خامسًا، اختبر مستخدمًا عاديًا ومدير نظام للتأكد من أن قائمة الشركات تظهر دون أن يتوسع نطاق الفروع المسموح بها.

## 7. الحكم النهائي

تم إصلاح الخلل البرمجي المؤكد في مسار وعقد قائمة الشركات، مع الحفاظ على ضوابط الأمان وعدم تعديل بيانات الإنتاج. إذا بقيت القائمة فارغة بعد نشر الإصلاح، فسيكون السبب المتبقي إعداد قاعدة البيانات المشار إليه في القسم الرابع، وليس عنصر الواجهة؛ وعندها يحدد ملف التشخيص السجل أو الشرط الذي يمنع الظهور بدقة.
