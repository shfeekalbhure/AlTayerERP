**آخر نقطة مراجعة:** الالتزام `0d9f1d4` — «دمج المرحلة الأولى: الدخول والجلسة والصلاحيات والتهيئة»  
**إعداد:** Manus AI

## 1. الملخص التنفيذي

مشروع **AlTayerERP** هو نظام تخطيط موارد مؤسسية (Enterprise Resource Planning — ERP) مبني على حل متعدد الطبقات باستخدام **.NET 8**، ويجمع بين واجهة سطح مكتب تعمل بتقنية **Windows Forms**، وواجهة خدمات **ASP.NET Core Web API**، وطبقتي المجال والبنية التحتية، مع قاعدة بيانات **MySQL** عبر **Entity Framework Core وPomelo**. يوضح الفرع `master` أن المشروع أنجز أساس المرحلة الأولى، بما في ذلك تسجيل الدخول، جلسة الخادم، الصلاحيات والأدوار، التهيئة المؤسسية، وعدد من وظائف المحاسبة وسير عمل السندات [1] [2] [3].

التقييم العام هو أن المشروع يمتلك **قاعدة وظيفية جيدة وقابلة للتوسع**، لكنه لا يزال في حالة **ما قبل الجاهزية الإنتاجية**. السبب الرئيس ليس غياب المكونات الأساسية، بل وجود بوابات جودة وأمان لم تُغلق بعد: لا توجد مشاريع اختبارات ظاهرة في الفرع المفحوص، ولم يمكن تنفيذ البناء داخل بيئة المراجعة لعدم توفر أدوات .NET، كما أن ملف إعدادات متتبعًا في Git يحتوي على بيانات اتصال افتراضية تتضمن كلمة مرور، وسياسة CORS الحالية مفتوحة بالكامل. لذلك يُوصى باعتبار النسخة الحالية **Baseline تطويرية للمرحلة الأولى** وليست إصدارًا إنتاجيًا.

## 2. منهجية المراجعة ومصادرها

تمت مراجعة نسخة نظيفة من الفرع `master`، وفحص بنية الحل وملفات المشاريع، وعدّ ملفات المصدر، وقراءة التوثيق وملفات SQL، وتحليل تهيئة API وآلية الجلسة، ومراجعة سجل الالتزامات والفروع وطلبات الدمج المفتوحة في GitHub. لم تُجرَ أي تغييرات على منطق النظام، ولم تُستخدم فروع العمل غير المدمجة لإثبات جاهزية `master`. ولذلك فإن هذا التقرير يصف **حالة النسخة المدمجة فقط**، مع ذكر الفروع وطلبات الدمج المنفصلة باعتبارها عناصر متابعة وليست جزءًا من خط الأساس الحالي.

## 3. البنية التقنية الحالية

يعتمد الحل على فصل واضح نسبيًا بين الطبقات. مشروع `AlTayerERP.API` يستضيف نقاط الوصول والخدمات، ومشروع `AlTayerERP.Core` يحتوي الكيانات، بينما يتولى `AlTayerERP.Infrastructure` سياق قاعدة البيانات وملفات EF Core Migrations. أما `AlTayerERP.Desktop` فيقدم واجهة Windows Forms، ويرتبط مباشرة بطبقة Core ويستهلك خدمات API عبر خدمات سطح المكتب [5].

| الطبقة | التقنية/المسؤولية | حالة المراجعة |
|---|---|---|
| واجهة الخدمات | ASP.NET Core Web API على `net8.0` مع Swagger | موجودة ومقسمة إلى Controllers وDTOs وServices |
| المجال | مشروع Core على `net8.0` | يحتوي كيانات المؤسسة والمحاسبة والصلاحيات |
| البنية التحتية | EF Core وPomelo MySQL على `net8.0` | يحتوي `AppDbContext` وMigrations |
| واجهة المستخدم | Windows Forms على `net8.0-windows` | شاشات الدخول والإعدادات والسندات والإدارة |
| قاعدة البيانات | MySQL، مع Migrations وملفات SQL توافقية | تحتاج توحيد مسار الترحيل ومصفوفة تحقق |
| التوثيق | Markdown عربي وقرارات ADR | موجود جزئيًا، ويحتاج استكمال الأدلة المعلنة في README |

## 4. ما تم إنجازه في خط الأساس الحالي

أظهر سجل الالتزامات أن الفرع الحالي يضم دمج المرحلة الأولى المتعلقة بالدخول والجلسة والصلاحيات والتهيئة، مع إصلاحات مرتبطة بتفويض الشاشات وفرض صلاحيات عمليات سند القبض وعزل إدارة السنوات المالية بسياق الجلسة [2]. كما أن تهيئة التطبيق تسجل خدمات توليد الأرقام، وسياسات مالية، ومصادقًا على الشاشات، وخدمات تدقيق واعتماد وترحيل السندات [6].

على المستوى الوظيفي، يغطي النظام الهيكل المؤسسي الأساسي، مثل الشركات والفروع والسنوات المالية، إضافة إلى المستخدمين والأدوار والصلاحيات. ويضم أيضًا وحدات الحسابات ودليل الحسابات ومراكز التكلفة والصناديق والعملات وأسعار الصرف وطرق الدفع، إلى جانب السندات المالية والاستعلام عن القيود وسير عمل الاعتماد والترحيل والتدقيق. هذا يدل على أن المشروع تجاوز مرحلة النموذج الأولي البسيط، لكنه يحتاج إلى إثبات متكامل عبر الاختبارات والتشغيل الفعلي قبل إعلان الاكتمال.

| المجال | الأدلة الموجودة في `master` | الحكم الحالي |
|---|---|---|
| الدخول والجلسة | `AuthController` و`ServerSessionService` و`FrmLogin` وطبقة تحقق عامة للطلبات | منفذ أساسيًا؛ يحتاج اختبار انتهاء الجلسة والتزامن |
| الأدوار والصلاحيات | Controllers للأدوار والصلاحيات، وخدمة `ScreenAuthorizationService` | منفذ على الخادم؛ يحتاج مصفوفة قبول شاملة |
| الهيكل المؤسسي | الشركات والفروع والمجموعات والسنوات والفترات المالية | منفذ جزئيًا؛ يحتاج تحقق قاعدة بيانات نظيفة |
| الإعدادات المرجعية | العملات، الصناديق، مراكز التكلفة، إعدادات الترقيم، البيانات المرجعية | موجود؛ يعتمد على توفر الجداول والبيانات المرجعية |
| السندات المالية | إنشاء وتعديل واستعلام واعتماد ورفض وترحيل وإلغاء ترحيل وتدقيق | غني وظيفيًا؛ يحتاج اختبارات تكامل وسيناريوهات صلاحيات |
| قاعدة البيانات | `AppDbContext` وMigration للجداول المحاسبية وملفات SQL توافقية | قابل للتشغيل نظريًا؛ مصدر الحقيقة يحتاج توحيدًا |
| تطبيق الجوال | فروع وطلبات دمج منفصلة عن `master` | ليس ضمن خط الأساس الحالي، ولا يُعد منجزًا في هذا التقرير |
| التوثيق | README عربي وقرارات ADR لمعيار الواجهة وجرد الشاشات | تأسيس جيد، لكنه غير مكتمل مقارنة بالبنية المعلنة |

## 5. نتائج التدقيق والمخاطر

### 5.1 مخاطر حرجة قبل أي نشر

**أولًا: وجود بيانات اتصال حساسة داخل ملف متتبع.** يحتوي `AlTayerERP.API/appsettings.json` على اتصال MySQL باستخدام المستخدم `root` وكلمة مرور مضمنة، كما أن الملف ليس مستبعدًا من Git [7] [8]. حتى لو كان الاتصال مخصصًا لبيئة محلية، فإن وجوده في المستودع يرفع احتمال إعادة استخدامه خارج بيئة التطوير أو تسريب بيانات اعتماد حقيقية بالخطأ. يجب إبطال أي كلمة مرور استُخدمت فعليًا، ونقل الاتصال إلى User Secrets أو متغيرات بيئة أو مدير أسرار، ووضع `appsettings.example.json` خاليًا من الأسرار.

**ثانيًا: سياسة CORS مفتوحة بالكامل.** تسجل `Program.cs` سياسة تسمح بأي أصل وأي أسلوب وأي رأس (`AllowAnyOrigin`, `AllowAnyMethod`, `AllowAnyHeader`) [6]. هذا مناسب فقط لتجارب محلية محدودة، ولا ينبغي أن يصل إلى بيئة اختبار مشتركة أو إنتاج. يلزم تحديد قائمة أصول موثوقة حسب البيئة، وتعطيل السياسة المفتوحة في إعدادات النشر.

**ثالثًا: غياب الاختبارات الآلية الظاهرة.** لم تظهر في النسخة المفحوصة مشاريع أو ملفات اختبار مخصصة. وبالنظر إلى حساسية المحاسبة وسير عمل الاعتماد والترحيل والصلاحيات، فإن غياب اختبارات وحدة وتكامل واختبارات قبول يمثل خطرًا مباشرًا على سلامة البيانات المالية. يجب اعتبار إنشاء حزمة اختبارات شرطًا لإغلاق المرحلة الأولى، لا تحسينًا اختياريًا.

### 5.2 مخاطر عالية ومتوسطة

**قابلية البناء لم تثبت في هذه المراجعة.** تعذر تنفيذ `dotnet build` لأن أداة `dotnet` غير مثبتة في بيئة المراجعة. هذه ليست نتيجة فشل في الكود، ولا يجوز تفسيرها على أنها نجاح؛ إنها **حالة تحقق غير منفذة** يجب إغلاقها على جهاز أو عامل CI يحتوي .NET 8 SDK وبيئة Windows المناسبة لبناء مشروع WinForms. يجب إضافة بناء آلي للـ API وCore وInfrastructure، وبناء Windows Desktop على عامل Windows.

**تعدد مصادر تحديث قاعدة البيانات.** يحتوي المشروع على EF Core Migrations، وفي الوقت نفسه على عدة ملفات SQL مؤرخة وملف توافق للمرحلة الأولى يطلب التنفيذ اليدوي وإعادة تشغيل API [9]. هذا النهج قد يكون ضروريًا أثناء الانتقال، لكنه يسبب خطر اختلاف بنية قاعدة البيانات بين البيئات وصعوبة معرفة التسلسل الصحيح. يلزم اعتماد مسار رئيسي واحد للترحيل، أو توثيق سياسة انتقالية صريحة تربط كل SQL بترحيل أو إصدار محدد.

**التوثيق أقل من البنية المعلنة.** يعلن README عن كراسة تنفيذية وأدلة للمطور وقاعدة البيانات وواجهات API وسجل إصدارات، بينما الملفات الموجودة في النسخة المفحوصة تركز على README وقراري ADR وجرد الشاشات. الفجوة لا تمنع التطوير، لكنها تزيد تكلفة التسليم والمراجعة، خصوصًا مع وجود وحدات محاسبية متعددة.

**تراكم العمل خارج `master`.** توجد ستة طلبات دمج مفتوحة تتعلق بقاعدة بيانات نظيفة، وطلبات الجوال، والشاشات المؤسسية، وتهيئة المرحلة الأولى [4]. هذا يعني أن صورة المشروع في `master` لا تعكس كل العمل الجاري. قبل اعتماد تقرير تقدم نهائي، يجب فرز الطلبات إلى: دمج، إغلاق، أو إبقاء مقصود مع توثيق سبب الاستبعاد.

## 7. خطة العمل ذات الأولوية

### الأولوية P0 — قبل الدمج أو النشر

ينبغي أولًا إزالة نص الاتصال الحساس من الملف المتتبع وتدوير كلمة المرور، ثم استبدال سياسة CORS المفتوحة بسياسة تعتمد على البيئة. بعد ذلك يجب تثبيت .NET 8 SDK في عامل بناء مناسب وتشغيل `restore`, `build`، ثم توثيق النتيجة. لا يُنصح بدمج فروع جديدة في خط إنتاج قبل إغلاق هذه النقاط.

### الأولوية P1 — إغلاق مخاطر الجودة الوظيفية

يجب إنشاء مشروع اختبارات Core لاختبار قواعد السندات والأرقام والسياسات، ومشروع اختبارات API لاختبار الجلسة والصلاحيات، واختبارات تكامل لسيناريوهات قاعدة البيانات النظيفة. كما يجب إعداد مصفوفة قبول تغطي: الدخول، اختيار الشركة والفرع والسنة، إنشاء السند، تعديله، مراجعته، اعتماده، ترحيله، إلغاء ترحيله، ومنع العمليات غير المصرح بها.

### الأولوية P2 — تنظيم التسليم والتوسع

بعد إغلاق المخاطر الحرجة، ينبغي توحيد مسار قاعدة البيانات، استكمال التوثيق العربي المعلن، وفرز طلبات الدمج المفتوحة. ويجب فصل تقييم الجوال عن تقييم `master` الحالي حتى يُدمج رسميًا ويجتاز نفس بوابات الأمان والاختبار.

## 8. التوصية النهائية

التوصية هي اعتماد النسخة الحالية باعتبارها **خط أساس تطويري للمرحلة الأولى**، مع منع تصنيفها كإصدار إنتاجي حتى إغلاق أسرار الإعدادات، وتقييد CORS، وإثبات البناء، وإضافة الاختبارات، واعتماد خطة قاعدة البيانات. نقطة القوة الرئيسة هي اتساع النموذج الوظيفي ووجود أساس واضح للجلسة والصلاحيات وسير عمل السندات. أما نقطة الضعف الرئيسة فهي أن مستوى التحقق الآلي والتشغيلي لا يزال أقل من حساسية نظام مالي متعدد الوحدات.
