# مصفوفة متطلبات المصادر — TransportERP

## المصدر

تم استخراج هذه النقاط من ملف **كراسة تصميم النظام المحاسبي والبيانات الأساسية — TransportERP، الإصدار 1.0** المرفق من مالك النظام بتاريخ 20 أغسطس 2026. وهو مرجع تصميم للمحاسبة والبيانات الأساسية ويغطي Desktop وAPI وMySQL وتطبيقات الجوال اللاحقة.

## قرارات ملزمة لتطبيق الجوال

| المجال | المتطلب المستخرج | أثر التنفيذ في Mobile Office |
|---|---|---|
| مصدر الحقيقة | API وقاعدة MySQL هما المرجع ولا قرار محاسبي نهائي في العميل. | تبقى كل عمليات الحفظ والاعتماد والترقيم عبر API؛ لا تولّد الواجهة أرقاماً نهائية أو قيوداً محلية. |
| المعمارية | Mobile → HTTP → API → Application → Domain، وContracts هي DTOs/Errors/Auth/Lookups فقط. | عميل `altayer-api.ts` هو نقطة الاتصال الوحيدة؛ لا اتصال مباشر بـ MySQL أو Entities. |
| نطاق الجلسة | شركة وفرع وسنة مالية وفترة وعملة افتراضية ودور واضح. | جلسة الدخول تحفظ الشركة والفرع والسنة في SecureStore ويجب أن تعرض في الواجهة. |
| العزل | CompanyId وBranchId وFiscalYearId/PeriodId تفرض خادمياً. | لا تُرسل الواجهة نطاقاً حراً خارج عقد الجلسة، وتعرض أخطاء النطاق الواردة من API. |
| الترقيم | خادمي ذري وفريد، لا `MAX+1` ولا إعادة استخدام بعد الإلغاء. | يمنع التطبيق إعادة الإرسال ويعرض خطأ `PAYMENT_REQUEST` مع توجيه إلى تشخيص الخادم. |
| الفصل والاعتماد | الإنشاء والمراجعة والاعتماد والترحيل صلاحيات مستقلة. | شاشة الاعتماد تستخدم عقد طلب اعتماد عام، وتطلب سبباً للرفض أو الإعادة. |
| القيد المرحّل | لا تعديل مباشر؛ التصحيح بعكس أو تسوية أو فك ترحيل مصرح مع سبب. | لا تعرض الواجهة تعديل سند مرحّل كمسار مباشر؛ يضاف لاحقاً سير عكس/تسوية. |
| البيانات الأساسية | الحسابات ومراكز التكلفة والصناديق والبنوك وطرق الدفع والعملات مراجع ذات مفاتيح لا نصوص حرة. | نموذج سند القبض يحمّل references ويستخدم المعرفات؛ يلزم تطبيق النمط نفسه على طلب الصرف. |
| مراكز التكلفة | تتحقق من النطاق والحالة والفترة، والإلزام يحدده الحساب أو نوع العملية. | تعرض الواجهة مركز التكلفة كمفتاح مرجعي، والخادم صاحب قرار القبول النهائي. |
| العملات | لكل سطر: عملة ومبلغ أجنبي وسعر صرف ومحلي ومصدر سعر؛ العملة الأساسية بسعر 1. | نموذج السند يرسل العملة وسعر الصرف ولا يفترض سعر سوق أو يعدل قيداً مرحلاً. |
| دورة حياة السند | مسودة → مراجعة → معتمد → ترحيل، مع إجراءات مقيّدة حسب الدور. | حفظ الطلب/السند يعرض حالة API ولا يقدم ترحيلاً محلياً أو اعتماداً ذاتياً. |
| التزام RTL | العربية أولاً وباتجاه RTL كامل. | كل الشاشات والمدخلات والرسائل مصممة بالعربية RTL. |

## شاشات محاسبية ذات أولوية مستقبلية للجوال

تسجل الكراسة شاشات: دليل الحسابات، مراكز التكلفة، الصناديق، الحسابات البنكية، طرق الدفع، السنوات والفترات، القيد اليومي، سند القبض، سند الصرف، التحويل، التسوية، الإقفال، العكس، دفتر اليومية، التقارير، والتسويات البنكية وطلبات الاعتماد. التطبيق الحالي يركز على سند القبض وطلبات الصرف والاعتماد والتشخيص؛ لا ينبغي إضافة شاشة إدارة بيانات أساسية على الجوال قبل تثبيت الصلاحيات وواجهات Lookup المناسبة.

## عقد الاعتماد V1

| المجال | القاعدة المعتمدة | أثر التطبيق |
|---|---|---|
| الحالة | `Pending → Approved / Rejected / Returned / Cancelled`. إعادة الفتح طلب محمي جديد ولا تمحو التاريخ. | لا يغيّر التطبيق الحالة محلياً إلا بعد نجاح API، ولا يعرض إعادة فتح كتحرير لتاريخ قرار سابق. |
| الإجراء المطلوب | `RequestedAction` رمز typed مسجل في Application، وليس نص فعل حر. | ترسل الواجهة أوامر القرار لمسارات API المقيدة فقط ولا تنشئ إجراء تنفيذ حر. |
| الاعتماد | يتطلب Pending وصلاحية ونطاق وفصل واجبات وأن الهدف ما زال مؤهلاً؛ القرار والإجراء والسجل تلتزم ذرياً. | زر الاعتماد يعرض رسالة API الدقيقة ولا يعيد المحاولة تلقائياً عند التعارض. |
| الرفض والإعادة | يضيفان قراراً إلى تاريخ append-only؛ الهدف لا ينفذ عند الرفض، وقد يعود قابلاً للتحرير عند الإعادة. | يلزم سبب قرار في الواجهة، مع عدم حذف أو استبدال القرارات السابقة. |
| فصل الواجبات | يمنع الخادم الاعتماد الذاتي حيث تطبق السياسة، وصلاحية الترحيل مستقلة عن صلاحية الاعتماد. | لا تعتمد الواجهة على إخفاء زر فقط؛ تفسر `SELF_APPROVAL_DENIED` للمستخدم. |
| التزامن | طلب أو هدف قديم يعيد `CONCURRENCY_CONFLICT` أو `APPROVAL_STATE_INVALID`؛ لا إعادة صامتة. | تعرض الواجهة «أعد تحميل الطلب» عند التعارض وتمنع تكرار إرسال القرار. |
| الأخطاء | `PERMISSION_DENIED` و`SCOPE_DENIED` و`STATE_TRANSITION_INVALID` و`IDEMPOTENCY_CONFLICT` أخطاء أعمال واضحة. | يضاف قاموس رسائل عربي لهذه الرموز في طبقة API ومركز التشخيص. |

## أولوية الإصدار 1.2

الإصدار **1.2** هو المرجع الأحدث الموفق، لكنه ينص صراحةً على أن التنفيذ البرمجي لا يبدأ قبل بوابة اعتماد الإصدار 1.13 والسياسات الضريبية والقانونية المحلية. لذلك يعامل التطبيق بطاقات الإصدار 1.2 كمرجع نطاق وضوابط، ولا يخترع أسماء حقول أو إجراءات فرعية لم ترد في بطاقة الشاشة المعتمدة.

| عنصر الإصدار 1.2 | قرار مواءمة التطبيق |
|---|---|
| 14 شاشة بيانات أساسية | لا تُدار من الجوال في الإصدار الحالي؛ تُستهلك فقط عبر Lookups خادمية للمراجع المصرح بها. |
| 44 شاشة محاسبية | الأولوية للجوال تبقى ACC-043 سند القبض، ACC-044 سند الصرف، وشاشات الاعتماد والرقابة، مع تقارير قراءة فقط لاحقاً. |
| الترقيم العام GEN-014 | أي تغيير أو تجاوز للترقيم إجراء محمي خادمي وقد يتطلب اعتماداً مستقلاً؛ لا تمنح الواجهة زر تجاوز. |
| الحسابات ومراكز التكلفة | الحساب التجميعي محظور للحركة، ومركز التكلفة يتحقق من النطاق والفعالية في API؛ تحفظ الجوال المفاتيح الراجعة من Lookup فقط. |
| النقد والبنوك | مصدر التحصيل/الصرف يجب أن يرتبط بصندوق أو بنك وحساب أستاذ وعملة صالحة؛ يوضح نموذج السند المراجع قبل الإرسال. |
| العمل المتصل/غير المتصل | لا مزامنة مالية صامتة في النسخة الحالية. عند انقطاع الشبكة لا يُنشأ قيد نهائي محلياً؛ يحتفظ التطبيق بالرسالة ويطلب إعادة الإجراء بعد عودة الاتصال. |

## خطة التنفيذ البرمجية — ضوابط التسليم

| بوابة أو قاعدة | الأثر على AlTayerERP Mobile Office |
|---|---|
| G3 — Screen | لا تبقى بيانات تجريبية في الشاشات المتصلة؛ كل قائمة أو عملية تعتمد على API أو تعرض حالة فارغة/خطأ صريحة. |
| G4 — Accounting | التوازن والفترة والترقيم والترحيل تتحقق في الخادم. الواجهة لا تنشئ قيداً نهائياً محلياً ولا تعيد الإرسال عشوائياً. |
| G5 — Release | لا تسلم النسخة قبل فحص TypeScript والاختبارات وخطة تحقق على جهاز فعلي ومراجعة عدم وجود أسرار داخل الحزمة. |
| Error Contract | تدعم الطبقة `code` و`message` و`fieldErrors` و`correlationId`، وتظهر الرسالة العربية الآمنة للمستخدم وتحتفظ بالمرجع التشخيصي. |
| Idempotency | عمليات الإنشاء الحساسة تحمل مفتاح عدم تكرار من العميل عند توفر دعم API؛ عمليات الإعادة تعتمد على نفس المفتاح لا إنشاء رقم جديد. |
| ACC-043/044 | سندا القبض والصرف معاملات: رأس + أسطر + إجماليات + مسار اعتماد + مرفقات وتدقيق؛ لا يُسمح بالترحيل أو الطباعة النهائية من دون تحقق خادمي. |
| ACC-057 | طلبات الاعتماد المحاسبية تستخدم عمليات صريحة Submit/Approve/Reject/Return مع سبب إلزامي للرفض أو الإعادة. |

## كراسة البوليصة المتكاملة V1 — نقاط التكامل المالي للجوال

| المتطلب | أثره على عمليات Mobile Office |
|---|---|
| البوليصة مسودة قبل الاعتماد | لا يُصدر الرقم الرسمي عند فتح البوليصة؛ الترقيم خادمي عند الاعتماد النهائي ولا يعاد استخدامه بعد الإلغاء. |
| التحصيل | كل دفعة تسجل مستقلة مع الطرف الدافع والطريقة والمبلغ والوقت والمحصل والفرع والمرجع المحاسبي. سند القبض لا يستبدل سجل التحصيل التشغيلي. |
| الدفع المختلط | الدافع قد يكون المرسل أو المستلم أو توزيعاً بينهما؛ طرق الدفع قد تكون نقداً أو آجلاً أو بنكاً أو خليطاً. يتطلب ذلك واجهة تخصيص دفعات لاحقة بدلاً من مبلغ واحد مفترض. |
| العملة | تحفظ البوليصة العملة وسعر الصرف المحاسبي؛ يجب تمريرهما إلى المرجع المالي ولا يعتمد العميل على سعر سوق حديث عند معالجة مستند قائم. |
| المحاسبة | إعادة ترحيل البوليصة لا تنشئ إيراد نقل جديداً. يربط التحصيل بصندوق/بنك/ذمم وبمرجع البوليصة، مع إمكانية الانتقال بين الأصل التشغيلي والقيد. |
| الاعتماد والتدقيق | صلاحيات الإنشاء والتعديل والاعتماد والإلغاء والطباعة والتحصيل والتسليم منفصلة؛ العمليات الحساسة تحتاج سبباً وسجل تدقيق ولا تحذف الحركة التاريخية. |
| بيانات البوليصة | تستخدم أطرافاً تشغيلية (مرسل/مستلم) لا دليل العملاء المحاسبي دائماً؛ لذلك لا يفرض تطبيق الجوال إنشاء Party_ID محاسبي عند كل بوليصة. |

### عناصر مؤجلة حتى توفر Contract للبوليصة

واجهة Mobile Office الحالية لا تضيف إنشاء أو تحرير بوليصات لأن وثيقة V1 لا تحدد مسارات API أو DTOs النهائية. يظل النطاق الحالي: تحميل مرجع بوليصة عند توفر Lookup خادمي، وتسجيل التحصيل/سند القبض عبر العقد المالي المعتمد. يلزم اعتماد Contract صريح للبوليصة قبل تنفيذ المسودات، الأصناف، الترحيل المتعدد، والتحصيل المختلط في الجوال.

## عناصر تحقق مطلوبة قبل التسليم التشغيلي

1. تأكيد أن API يضع نطاق الشركة والفرع والسنة والفترة من جلسة موثقة وليس من قيم يختارها العميل.
2. اختبار رفض الحساب التجميعي أو مركز التكلفة الموقوف أو الفترة المغلقة من داخل API.
3. اختبار حسابات العملة الأساسية والأجنبية، بما فيها تطابق المحلي مع السعر المعتمد.
4. اختبار منع اعتماد منشئ السند لطلبه إذا كانت السياسة الخادمية تمنع ذلك.
5. اختبار فشل الترقيم والتأكد من عدم إنشاء طلب مكرر عند إعادة محاولة المستخدم.
