# تصميم واجهات AlTayerERP Mobile Office

## الهدف والنطاق

التطبيق هو واجهة جوال عربية تعمل باتجاه **RTL** لموظف AlTayerERP، وتحوّل نتائج فريق المراجعة إلى سير عمل تشغيلي واضح: فحص جاهزية الاتصال، الدخول واختيار الشركة، إنشاء طلبات الصرف وسندات القبض، متابعة طلبات الاعتماد، وعرض تشخيص قابل للتنفيذ عند فشل الاتصال أو الترقيم. يركّز الإصدار الأول على تجربة محلية تفاعلية ببيانات تجريبية منظمة، ولا يدّعي اتصالاً مباشراً بقاعدة بيانات أو بالخادم الإنتاجي.

## مبادئ الواجهة

يُصمَّم التطبيق للوضع الرأسي **9:16** والاستخدام بيد واحدة. يتبع نمط iOS الرئيسي: شريط علوي بسيط، مناطق لمس لا تقل عن 44 نقطة، بطاقات مرتفعة باعتدال، تسلسل نصي واضح، وأزرار إجراءات أساسية مثبتة في أسفل النماذج عند الحاجة. تُكتب كل النصوص التشغيلية بالعربية، وتبقى الأكواد التقنية مثل `PAYMENT_REQUEST` داخل شارات أحادية النمط لتسهيل التشخيص.

## قائمة الشاشات

| المجموعة | الشاشة | المحتوى والوظائف الرئيسية |
|---|---|---|
| الجلسة والاتصال | شاشة الدخول | مؤشر حالة الخادم، اختيار الشركة، بيانات المستخدم، إكمال الدخول. |
| الجلسة والاتصال | إعداد الاتصال | وضع USB أو Wi‑Fi أو تلقائي، عنوان الخادم، المنفذ `5021`، اختبار `/api/health`. |
| التشغيل | لوحة المكتب | ملخص حالة الجلسة، عناصر انتظار الاعتماد، اختصارات طلب الصرف وسند القبض، حالة الاتصال. |
| التشغيل | طلبات الصرف | قائمة حسب الحالة مع رقم الطلب والمستفيد والمبلغ والتاريخ. |
| التشغيل | طلب صرف جديد | رأس الطلب، أسطر محاسبية، إجمالي، حفظ مسودة أو حفظ وإرسال. |
| التشغيل | سند قبض جديد | بيانات الرأس والمرجع والملاحظات وأسطر القيد ومفتاح طلب الاعتماد. |
| الاعتماد | طلبات الاعتماد | قائمة عامة مبنية على نموذج طلب اعتماد، لا على طلبات الصرف فقط. |
| الاعتماد | تفاصيل طلب الاعتماد | المرجع والسبب والمبلغ ومسار القرار: مراجعة، اعتماد، رفض، إعادة. |
| التشخيص | مركز التشخيص | حالات `api/health`، الترقيم، الشبكة، الإجراء المقترح، وسجل أحداث محدود. |
| الإعدادات | إعدادات التطبيق | تفضيلات المظهر، عنوان الخادم، ملخص النسخة، وتوضيح التدفق الصحيح Mobile → API → MySQL. |

## تدفقات المستخدم الأساسية

| التدفق | الخطوات |
|---|---|
| الدخول الآمن | فتح التطبيق → فحص `/api/health` → عند النجاح اختيار الشركة → إدخال بيانات المستخدم → الانتقال إلى لوحة المكتب. عند الفشل تظهر بطاقة تشخيص بدلاً من قائمة شركات فارغة. |
| إنشاء طلب صرف | لوحة المكتب → طلب صرف جديد → تعبئة المستفيد وأسطر الطلب → اختيار حفظ مسودة أو حفظ وإرسال → عرض حالة الحفظ أو بطاقة خطأ الترقيم مع الإجراء المطلوب. |
| إنشاء سند قبض | لوحة المكتب → سند قبض جديد → إدخال الرأس والمرجع والأسطر → تفعيل/إلغاء طلب الاعتماد → حفظ الطلب → عرض رقم السند وحالة الاعتماد. |
| معالجة اعتماد | لوحة المكتب أو تبويب الاعتماد → اختيار طلب → مراجعة البيانات → اعتماد أو رفض أو إعادة مع سبب → تحديث الحالة محلياً وإظهار رسالة نتيجة. |
| معالجة اتصال أو ترقيم | ظهور خطأ → فتح مركز التشخيص → قراءة نوع الخطأ والمسار → نسخ خطوة العلاج أو الانتقال لإعداد الاتصال → إعادة اختبار الحالة. |

## نماذج البيانات الأولية

تستخدم الواجهة نماذج محلية واضحة قابلة للاستبدال لاحقاً بعقود API: `ConnectionHealth` و`CompanyOption` و`PaymentRequest` و`VoucherDraft` و`ApprovalRequest` و`DiagnosticEvent`. كما يحتفظ التطبيق بحالة الجلسة وإعداد الاتصال محلياً فقط في الإصدار الأول، دون تضمين كلمات مرور أو عناوين إنتاجية ثابتة.

## حدود الإصدار الأول

لا ينفذ التطبيق أي تعديل على قاعدة البيانات ولا يدعي تشغيل API حقيقي من هذه الواجهة. ستُعرض مشكلة ترقيم `PAYMENT_REQUEST` كحالة تشغيلية مفهومة، مع التفريق بين فقدان الإعداد، تعطيله، وتأخر استجابة الخادم. ربط الواجهات مع API الحقيقي يتطلب في مرحلة لاحقة توثيق العقود وإدارة رموز الدخول في تخزين آمن.
