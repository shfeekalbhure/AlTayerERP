## 1. تعريف الانحراف

المقصود بالانحراف هو اختلاف واحد أو أكثر بين:

- Entity في C#.
- `DbSet` وFluent API.

- Migration.
- SQL يدوي.
- الاستخدام الفعلي في API/Desktop/Mobile.

## 2. الانحرافات الرئيسية المؤكدة

### 2.1 عدد الجداول مقابل Migrations

- `AppDbContext`: 41 DbSet.
- Migration تنفيذية: واحدة.
- Migration الوحيدة تنشئ جدولي القيود فقط.

**النتيجة:** 39 جدولاً على الأقل لا يمكن إثبات إنشائها من Migrations الحالية.

### 2.2 TenantGroup

- Entity يحتوي خصائص موسعة مثل `Short_Name`, `Parent_Group_ID`, `Main_Company_ID`, `Sort_Order` وحقول تدقيق.
- Fluent API يتجاهل عدداً كبيراً منها لأنها غير موجودة في جدول المرحلة الحالية.
- SQL تاريخي يضيف بعض هذه الأعمدة ثم يعدلها.

**القرار المقترح:** تحديد نموذج نهائي واحد للمجموعة التجارية قبل Baseline؛ لا يجوز أن تبقى الخصائص في Entity ثم تُتجاهل بلا قرار معماري.

### 2.3 Journal Entries

- Migration تستخدم `Branch_ID varchar(50)`.
- بقية النظام تتعامل غالباً مع `Branch_ID int`.
- `Created_By/Updated_By/Posted_By` في Migration نصوص `varchar(50)`، بينما `User_ID` في النظام عدد صحيح.

**الخطر:** منع FK حقيقية وظهور تحويلات يدوية في API.

### 2.4 Snapshot

- Snapshot لا يمثل 41 DbSet الحالية بصورة قابلة للاعتماد.
- لا يثبت Collation عامة.
- بعض النصوص تظهر `longtext` بسبب غياب `HasMaxLength`.

**القرار المقترح:** لا تولد Migration جديدة من Snapshot الحالي قبل إعادة بناء النموذج في فرع Baseline.

### 2.5 SQL Compatibility Scripts

- سكربتات `CREATE TABLE IF NOT EXISTS` و`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` مصممة لترقية قواعد موجودة.
- هذه السكربتات لا تمثل ترتيب إنشاء قاعدة جديدة.
- بعض الجداول لها تعريف في SQL ولا يوجد لها Migration.

**الخطر:** جهازان يشغلان مجموعات سكربتات مختلفة وينتهيان بمخططين مختلفين.

### 2.6 Collation

- SQL المرحلة الأولى يستخدم `utf8mb4_unicode_ci` في عدة ملفات.
- Migration القيود تستخدم `utf8mb4` دون Collation.
- لا يوجد `modelBuilder.UseCollation` موحد.

**الخطر:** اختلاف Collation بين أعمدة المفاتيح النصية والفهارس.

## 4. الجداول التي قد تتغير وقت تشغيل API

لا يوجد `EnsureCreated` أو `Migrate` في `Program.cs`. لذلك API لا ينشئ المخطط تلقائياً. التغيير وقت التشغيل يقتصر على بيانات مرجعية عند تفعيل Bootstrap:

- كتالوج الشاشات.
- مراجع أنواع/حالات السندات وطرق السداد.

أي Controller يستخدم SQL نصياً قد ينفذ DML أو يعتمد على جدول موجود، لكنه ليس Baseline.

## 5. المطلوب لإغلاق Drift

1. اعتماد جدول نهائي لكل Entity.
2. اعتماد أنواع المفاتيح.
3. استكمال Fluent API.
4. إلغاء الاعتماد على SQL التراكمي كمسار إنشاء.
5. إنشاء Baseline واحدة فقط بعد الاعتماد.
6. مقارنة SQL المولد مع Data Dictionary.
7. اختبار إنشاء قاعدة فارغة مرتين وإثبات تطابق المخطط.
