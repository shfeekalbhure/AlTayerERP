## 3. التصنيف حسب الفئة

### مخطط أساسي جزئي

- system settings.
- fiscal periods.
- exchange rates.
- bank accounts.

هذه الملفات ليست Baseline كاملة لأنها لا تنشئ العلاقات المؤسسية والأمنية وبقية المحرك المالي.

### توافق مؤقت

- `phase1_setup_compatibility.sql`.

يجب ألا يُستخدم لإنشاء القاعدة الجديدة؛ وظيفته ترقية نسخة قديمة غير معروفة الحالة.

### ترقية قديمة

- Complete Receipt Voucher Workflow.
- Add Amount To Financial Voucher Headers.

يجب استخراج النتيجة النهائية المطلوبة ودمجها في النموذج، لا تشغيلها بعد Baseline.

### إصلاح تاريخي

- Restore Journal Entry Tables.
- Fix Voucher Review Action Constraint.

هذه الملفات دليل على drift وتشغيل يدوي سابق، وليست مصدر الحقيقة النهائي.

### Seed Data

- بيانات الإعدادات المرجعية داخل سكربت system settings إن وجدت.
- Seeders البرمجية للشاشات ومراجع السندات ليست ملفات SQL، لكنها يجب تصنيفها ضمن Seed مستقل.

### مكرر/متعارض

- تعريف جداول القيود موجود في Migration وفي سكربت Restore؛ هذا تكرار ومتعارض محتمل.
- بعض جداول الإعدادات معرفة في Entity وSQL يدوي ولا توجد في Migration.

### مهجور

لا يُعلن أي ملف مهجور في هذه المرحلة دون مقارنة نهائية مع مخطط التشغيل وقرارات الأعمال.

## 4. قواعد المرحلة الثانية المقترحة

1. لا يُحذف أي سكربت تاريخي؛ ينقل لاحقاً إلى `Database/Legacy` بعد اعتماد المالك فقط.
2. Baseline تنشأ من EF Model النهائي، لا من تجميع السكربتات.
3. Seed Data تحفظ في ملفات/Seeders منفصلة وقابلة لإعادة التشغيل.
4. كل إصلاح تاريخي يُحول إلى قيد أو Default أو Index داخل Fluent API.
5. يمنع وجود مصدرين ينشئان الجدول نفسه.

## 5. نقاط تحتاج قراراً

- هل سكربت Restore للقيود يمثل المخطط الأحدث أم Migration؟
- هل `Amount` في رأس السند قيمة مخزنة أم محسوبة من التفاصيل؟
- هل قيود مراجعة السند الحالية نهائية؟
- ما البيانات المرجعية التي يجب إدخالها تلقائياً عند إنشاء قاعدة نظيفة؟

## 6. تأكيد

لم يُنفذ أو يُعدل أو يُحذف أي سكربت.
