# سجل قرارات قاعدة البيانات

**فرع التدقيق:** `agent/phase1-clean-database-baseline`  
**SHA نقطة البداية:** `4c40992a9c62ece3033bc7f652ceef2817cfe616`  
**قاعدة هذه المرحلة:** توثيق فقط؛ لا Migration ولا SQL ولا تعديل قاعدة.

## صيغة القرار

لكل قرار: الحالة، البدائل، المزايا والعيوب، الأثر، المقترح، والجهة المعتمدة.

## DB-DEC-001 — عزل عمل Baseline

- **الحالة:** معتمد.
- **البدائل:** العمل على الفرع الموحد أو فرع مستقل.
- **القرار:** فرع مستقل `agent/phase1-clean-database-baseline`.
- **الأثر:** يمنع اختلاط تدقيق قاعدة البيانات بأعمال الشاشات.
- **جهة الاعتماد:** مالك المشروع.

## DB-DEC-002 — حماية القاعدة القديمة

- **الحالة:** معتمد.
- **القرار:** لا أوامر كتابية ولا Migrations على `altayer_erp_db` ضمن مشروع Baseline.
- **الممنوع:** `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `INSERT`, `UPDATE`, `DELETE` وأي Migration.
- **جهة الاعتماد:** مالك المشروع.

## DB-DEC-003 — توقيت إنشاء القاعدة الجديدة

- **الحالة:** معتمد.
- **القرار:** لا تُنشأ `altayer_erp_db_clean` قبل اعتماد تقرير المرحلة الأولى.
- **جهة الاعتماد:** مالك المشروع.

## DB-DEC-004 — مصدر الحقيقة للمخطط

- **الحالة:** مقترح — يحتاج اعتماد.
- **البدائل:** Migrations فقط؛ SQL فقط؛ خليط دائم.
- **المزايا:** Migration واحدة قابلة للتكرار، Snapshot متزامن، مراجعة واضحة.
- **العيوب:** يتطلب استخراج المتطلبات من 28 سكربتًا تاريخيًا.
- **المقترح:** `AppDbContext + Fluent API + EF Migrations` هي المصدر الوحيد للمخطط. SQL اليدوي لا ينشئ المخطط بعد Baseline.
- **الأثر:** كل إنشاء أو تغيير مخطط مستقبلي يمر عبر Migration مراجعة.
- **جهة الاعتماد:** المالك + معماري النظام.

## DB-DEC-005 — نوع `Group_ID`

- **الحالة:** مفتوح.
- **البدائل:** `CHAR(36)` GUID؛ `VARCHAR(50)`؛ رقم داخلي.
- **المزايا/العيوب:** GUID يدعم العزل والتوليد الموزع لكنه أكبر في الفهارس؛ الرقم أصغر لكنه يتطلب ترحيلًا واسعًا.
- **المقترح:** إبقاؤه نصيًا، والأفضل `CHAR(36)` إن ثبت أن كل القيم GUID، وإلا `VARCHAR(50)`.
- **الأثر:** `companies.Group_ID` والعلاقات المؤسسية وCollation.
- **جهة الاعتماد:** المالك بعد فحص القيم.

## DB-DEC-006 — نوع `Company_ID`

- **البدائل:** `CHAR(36)` GUID؛ `VARCHAR(50)`؛ رقم داخلي.
- **المقترح:** إبقاؤه نصيًا لتقليل أثر الترحيل، مع طول موحد يحدد بعد فحص القيم.
- **الأثر:** معظم جداول النظام والأمن والمحاسبة.
- **جهة الاعتماد:** المالك.

## DB-DEC-007 — نوع `Branch_ID`

- **المزايا:** `INT` يطابق PK والجلسات وطلبات الصرف ويصغر الفهارس.
- **العيوب:** يحتاج ترحيل قيم السندات والقيود النصية.
- **المقترح:** `INT` داخلي و`Branch_Code` نصي منفصل.
- **المرجع:** `Branch_ID_Normalization_Assessment.md`.
- **جهة الاعتماد:** المالك بعد فحص القيم القديمة.

## DB-DEC-012 — سياسة IDs المرجعية

- **الحالة:** مقترح.
- **البدائل:** IDs رقمية؛ Codes نصية كـPK.
- **المقترح:** الجداول المرجعية المحدودة تستخدم `INT AUTO_INCREMENT` كـPK، وكود أعمال نصي Unique منفصل: Currency, VoucherType, Status, PaymentMethod, BranchType, Country/Governorate/City.
- **الأثر:** FKs أصغر واستقرار عند تغيير الأسماء والأكواد.
- **جهة الاعتماد:** معماري النظام + المالك.

## DB-DEC-013 — Collation النهائية

- **الحالة:** مقترح — تحتاج اعتماد المالك.
- **البدائل:** `utf8mb4_0900_ai_ci`; `utf8mb4_unicode_ci`.
- **المقترح الوحيد:** `utf8mb4_unicode_ci` للـBaseline الأولى.
- **السبب:** إصدارات MySQL في التطوير والاختبار والإنتاج غير موثقة، ولا يوجد نفي موثق لوجود MariaDB/MySQL أقدم؛ كما أنها تطابق أغلب السكربتات الحالية وتقلل مخاطر نقل البيانات القديمة. يمكن الترقية إلى 0900 لاحقًا بعد توحيد البيئات.
- **الأثر:** كل الأعمدة النصية، الفهارس، Unique وFK النصية.
- **جهة الاعتماد:** المالك بعد توثيق الإصدارات.

## DB-DEC-014 — سياسة أسماء الجداول

- **الحالة:** مقترح.
- **البدائل:** PascalCase تاريخي؛ snake_case lowercase.
- **المقترح:** `snake_case` بحروف صغيرة لكل الجداول والأعمدة مع أسماء EF صريحة.
- **السبب:** تجنب حساسية حالة الأحرف بين Windows/Linux ومشكلة `Tenant_Branches` مقابل `tenant_branches`.
- **جهة الاعتماد:** معماري النظام.

## DB-DEC-015 — سياسة حقول التدقيق

- **الحالة:** مقترح — يحتاج اعتماد.
- **البدائل:** IDs نصية Snapshot؛ FK رقمية؛ كلاهما.
- **المقترح:** `Created_By_User_ID/Updated_By_User_ID INT?` كـFK `SET NULL`، مع Snapshot اختياري للاسم/الكود في السجلات الرقابية طويلة العمر. لا يقبل العميل قيم التدقيق.
- **الأثر:** تحويل حقول نصية حالية وتحليل القيم غير الرقمية.
- **جهة الاعتماد:** المالك + الأمن والرقابة.

## DB-DEC-016 — سياسة التاريخ والوقت

- **الحالة:** مقترح.
- **البدائل:** Local server time؛ UTC؛ timestamps مع offset.
- **المقترح:** تخزين UTC في `DATETIME(6)` لكل أحداث النظام، والتحويل للتوقيت المحلي في الواجهات. تواريخ الأعمال مثل `Voucher_Date` و`Fiscal_Date` تبقى `DATE/DATETIME` بحسب المعنى دون تحويل زمني غير مقصود.
- **جهة الاعتماد:** معماري النظام.

## DB-DEC-017 — سياسة الحذف

- **الحالة:** مقترح.
- **المقترح:**
  - الهيكل المؤسسي والأدلة والسندات: `Restrict/NoAction` + إيقاف منطقي.
  - تفاصيل الرأس غير المرحلة: `Cascade` عند حذف الرأس المسموح فقط.
  - سجلات التدقيق والحركات: Append-only، لا Cascade.
  - علاقات المستخدم الاختيارية: `SetNull`.
- **جهة الاعتماد:** المالك + المحاسبة.

## DB-DEC-018 — Check Constraints وDefaults

- **الحالة:** مقترح.
- **المقترح:** تعريف القيود داخل Fluent/Migration: أسعار > 0، تواريخ صحيحة، Debit/Credit، حالات workflow، Defaults للحالة والتاريخ. لا تعتمد Triggers تاريخية كمصدر وحيد دون قرار.
- **جهة الاعتماد:** معماري النظام + المحاسبة.

## DB-DEC-019 — مصير Migrations القديمة

- **الحالة:** مقترح — يحتاج اعتماد.
- **القرار:** لا تُحذف من الفرع الأصلي. بعد اعتماد المرحلة الثانية يُنشأ تاريخ Baseline نظيف على فرع العمل، مع حفظ التاريخ القديم كمرجع.
- **جهة الاعتماد:** المالك.

## DB-DEC-020 — مصير SQL القديم

- **الحالة:** مقترح — يحتاج اعتماد.
- **القرار:** لا يُشغل على القاعدة النظيفة. تستخرج منه المتطلبات، ثم ينقل لاحقًا إلى `Database/Legacy` دون حذف.
- **جهة الاعتماد:** المالك.

## DB-DEC-021 — SchemaInitializer

- **الحالة:** مفتوح/يحتاج معالجة في المرحلة الثانية.
- **الوضع:** `PaymentRequestSchemaInitializer` يحتوي DDL عبر `ExecuteSqlRawAsync` لإنشاء ثلاثة جداول. لم يثبت تسجيله أو استدعاؤه في `Program.cs` الحالي، لكنه مصدر DDL برمجي خطر.
- **المقترح:** إزالته من مسار التشغيل بعد تغطية الجداول بـMigration؛ يمكن تحويله إلى فاحص قراءة فقط مؤقتًا.
- **جهة الاعتماد:** معماري النظام.

## DB-DEC-022 — Seeders

- **الحالة:** مقترح.
- **القرار:** Seeders لا تنشئ مخططًا؛ تعمل بعد Migration فقط، وتكون idempotent. يسمح بالمراجع الأساسية فقط، ولا شركات/مستخدمين/أرصدة تجريبية.
- **جهة الاعتماد:** المالك.

## DB-DEC-023 — Runtime schema mutation

- **الحالة:** مقترح — يحتاج اعتماد نهائي.
- **القرار:** ممنوع DDL وقت تشغيل API. تطبيق Migrations عملية نشر صريحة ومراقبة.
- **جهة الاعتماد:** المالك + DevOps.

## DB-DEC-024 — إثبات جاهزية القاعدة النظيفة

- **الحالة:** معتمد مبدئيًا.
- **الشروط:** إنشاء قاعدتين فارغتين من Baseline وإثبات تطابقهما، فحص Collation وFKs، نجاح API/Desktop/Mobile وظيفيًا، وخطة رجوع واعتماد المالك.
