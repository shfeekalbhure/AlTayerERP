# سجل قرارات قاعدة البيانات

## DB-DEC-001 — عزل عمل Baseline

- **الحالة:** معتمد.
- **القرار:** كل أعمال التدقيق وBaseline على فرع `agent/phase1-clean-database-baseline`.
- **نقطة البداية:** `4c40992a9c62ece3033bc7f652ceef2817cfe616`.
- **القيود:** لا تعديل مباشر على `agent/unified-phase1-screens` ولا دمج إلى `master`.

## DB-DEC-002 — حماية القاعدة القديمة

- **الحالة:** معتمد.
- **القرار:** قاعدة `altayer_erp_db` للقراءة/الاختبار الحالي فقط، ولا تنفذ عليها أوامر كتابية ضمن مشروع Baseline.
- **الممنوع:** `ALTER`, `DROP`, `TRUNCATE`, `CREATE`, `UPDATE`, `DELETE`, `INSERT` وأي Migration.

## DB-DEC-003 — عدم إنشاء القاعدة الجديدة في مرحلة التدقيق

- **الحالة:** معتمد.
- **القرار:** لا تُنشأ `altayer_erp_db_clean` قبل اعتماد تقرير المرحلة الأولى.

## DB-DEC-004 — مصدر الحقيقة النهائي

- **الحالة:** مقترح، يحتاج اعتماد.
- **القرار المقترح:** `AppDbContext + Fluent API + Baseline Migration` هي مصدر المخطط؛ SQL اليدوي يصبح مرجعاً تاريخياً أو Seed منفصلاً.
- **السبب:** وجود 41 DbSet مقابل Migration واحدة وسكربتات تراكمية متعارضة.

## DB-DEC-005 — أنواع المفاتيح المؤسسية

- **الحالة:** يحتاج قرار.
- **الخيارات:**
  1. `Group_ID` و`Company_ID` نصوص GUID بطول ثابت.
  2. تحويلهما إلى أرقام داخلية مع Codes نصية منفصلة.
- **الأثر:** كل FKs، الفهارس، حجم المفاتيح، ونقل البيانات.

## DB-DEC-006 — Branch_ID

- **الحالة:** يحتاج قرار عاجل.
- **الوضع:** غالبية النظام تستخدم `int`، بينما Migration القيود تستخدم `varchar(50)`.
- **التوصية:** اعتماد `int` في كل الجداول ما لم يوجد سبب أعمال موثق للمعرف النصي.

## DB-DEC-007 — Account_ID وCost_Center_ID

- **الحالة:** يحتاج قرار عاجل.
- **الوضع:** Migration القيود تستخدم نصوصاً؛ يوجد التباس بين PK وكود الحساب/المركز.
- **التوصية:** فصل المعرف الداخلي عن كود الأعمال إن لم يكن الكود نفسه PK معتمداً.

## DB-DEC-008 — User references في التدقيق

- **الحالة:** يحتاج قرار.
- **الخيارات:**
  - FK عددية nullable إلى `users` مع `SetNull`.
  - Snapshot نصي يحفظ هوية المنفذ وقت العملية بلا FK.
- **التوصية:** FK عددية مع حفظ اسم snapshot اختياري للتقارير التاريخية.

## DB-DEC-009 — Collation

- **الحالة:** غير معتمد بعد.
- **الخيارات:**
  - `utf8mb4_0900_ai_ci`: مفضل عند MySQL 8 حصراً.
  - `utf8mb4_unicode_ci`: أوسع توافقاً مع MySQL أقدم/MariaDB ويطابق سكربتات حالية.
- **القرار المطلوب:** توثيق إصدارات كل البيئات أولاً.

## DB-DEC-010 — Migrations التاريخية

- **الحالة:** مقترح، يحتاج اعتماد.
- **القرار المقترح:** لا تحذف من الفرع الأصلي. في فرع Baseline فقط، بعد الاعتماد، يُنشأ تاريخ Migration نظيف يمثل المخطط النهائي.

## DB-DEC-011 — سكربتات SQL التاريخية

- **الحالة:** مقترح.
- **القرار:** لا تُشغل على القاعدة النظيفة. تُستخرج منها المتطلبات النهائية ثم تصنف لاحقاً تحت Legacy دون حذف.

## DB-DEC-012 — Seed Data

- **الحالة:** مقترح.
- **القرار:** فصل Seed عن DDL، وأن يكون idempotent ومحدوداً إلى المراجع الأساسية:
  - الشاشات والصلاحيات.
  - أنواع وحالات السندات.
  - طرق السداد.
  - أنواع الفروع.
- **الممنوع:** إدخال شركات أو مستخدمين أو أرصدة تجريبية ضمن Baseline.

## DB-DEC-013 — Runtime schema mutation

- **الحالة:** معتمد مبدئياً.
- **القرار:** API لا ينشئ أو يعدل المخطط وقت التشغيل. تطبيق Migrations يكون عملية نشر صريحة ومراقبة.

## DB-DEC-014 — إثبات الجاهزية

- **الحالة:** معتمد مبدئياً.
- **لا تعتبر القاعدة جاهزة إلا بعد:**
  1. إنشاء قاعدة فارغة من Baseline.
  2. مطابقة schema مع Data Dictionary.
  3. فحص Collation لكل الأعمدة النصية.
  4. نجاح API وDesktop وMobile وظيفياً.
  5. إعادة إنشاء قاعدة ثانية من الصفر وإثبات التطابق.
  6. اعتماد مالك المشروع.

## سجل المرحلة الحالية

- لم تنشأ قاعدة جديدة.
- لم تنفذ Migration أو SQL.
- لم تتغير Entities أو AppDbContext.
- لم يتغير Connection String.
- لم يحدث دمج.
