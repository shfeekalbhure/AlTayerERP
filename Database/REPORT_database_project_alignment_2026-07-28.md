# تقرير مراجعة ومطابقة قاعدة بيانات AlTayerERP مع المشروع

**التاريخ:** 2026-07-28  
**الفرع:** `agent/unified-phase1-screens`  
**قاعدة البيانات المعتمدة:** `altayer_erp_db`  
**النسخة المرجعية:** آخر ملف SQL مرفوع من مالك المشروع  
**نطاق المراجعة:** قاعدة البيانات كاملة مقابل `AlTayerERP.Core` و`AlTayerERP.Infrastructure` و`AlTayerERP.API` وما تعتمد عليه شاشات سطح المكتب.

## 1. الملخص التنفيذي

قاعدة البيانات ليست تالفة، لكنها حالياً **قاعدة هجينة** تحتوي جداول المرحلة الحالية إلى جانب جداول قديمة من تصميم سابق. يوجد 68 جدولاً، بينما `__EFMigrationsHistory` يسجل ترقية EF واحدة فقط؛ وهذا يثبت أن معظم البنية أُنشئت أو عُدلت بواسطة ملفات SQL يدوية خارج سجل EF.

لا يجوز حذف الجداول القديمة مباشرة، لأنها ما زالت مرتبطة بمفاتيح خارجية حتى لو كانت فارغة. المعالجة المعتمدة هي:

1. تثبيت الجداول الحالية المستخدمة فعلياً بواسطة API.
2. عزل الجداول القديمة بإعادة تسمية آمنة فقط عند التأكد أنها فارغة.
3. توحيد الأنواع والفهارس والعلاقات تدريجياً.
4. عدم تعديل بيانات تشغيلية أو حذفها.

## 2. التعارضات الحرجة المؤكدة

### DB-001 — جدول الحسابات البنكية لا يطابق الكود

الكود الحالي يتوقع:

- `Bank_Account_ID INT AUTO_INCREMENT`
- `Bank_Code`
- `Account_No`
- `GL_Account`
- `Branch_Name`

بينما قاعدة البيانات الحالية تحتوي جدولاً قديماً بمواصفات مختلفة:

- `Bank_Account_ID VARCHAR(36)`
- `Account_Number`
- `Account_ID`
- لا يحتوي `Bank_Code` أو `Account_No` أو `GL_Account` أو `Branch_Name`

**الأثر:** فتح شاشة الحسابات البنكية أو الحفظ منها قد ينتج أخطاء أعمدة أو تحويل نوع المفتاح.

**حالة البيانات في النسخة المرفوعة:** الجدول فارغ.  
**الحل الآمن:** إعادة تسمية الجدول القديم إلى `bank_accounts_legacy` مع بقاء علاقاته القديمة، ثم إنشاء جدول `bank_accounts` المطابق للكود.

### DB-002 — فهرس رقم السند لا يطابق إعداد Entity Framework

الكود يعتمد فهرساً فريداً مركباً:

`Branch_ID + Fiscal_Year_ID + Voucher_Type_ID + Voucher_No`

بينما قاعدة البيانات تفرض فهرساً فريداً عالمياً على:

`Voucher_No`

**الأثر:** يمنع تكرار الرقم نفسه بصورة صحيحة بين الفروع أو السنوات أو أنواع السندات، رغم أن نظام الترقيم مصمم حسب النطاق.

**الحل:** إنشاء الفهرس المركب ثم إزالة الفهرس العالمي القديم.

### DB-003 — نوع الفرع في السندات والقيود غير موحد

- `tenant_branches.Branch_ID` نوعه `INT`.
- `financial_voucher_headers.Branch_ID` نوعه `VARCHAR(50)`.
- `journal_entry_headers.Branch_ID` نوعه `VARCHAR(50)`.
- `payment_requests.Branch_ID` نوعه `INT`.

**الأثر:** لا يمكن إنشاء مفتاح خارجي مباشر للسندات والقيود إلى جدول الفروع، ويضطر الكود إلى التحويل النصي إلى رقم.

**الحل المستهدف:** توحيد `Branch_ID` إلى `INT` في المحرك المالي والكود مع ترقية بيانات آمنة. هذا التغيير مؤجل إلى حزمة مستقلة لأنه يمس كيانات وخدمات متعددة.

### DB-004 — ازدواج جدول الفروع

يوجد:

- `tenant_branches`: الجدول الحالي المستخدم بواسطة `AppDbContext`.
- `branches`: جدول قديم بمعرف `VARCHAR(36)`.

الجدول القديم مرتبط بجداول `voucher_headers` القديمة.

**الحل:** لا حذف. يصنف كجدول Legacy إلى أن تُغلق كل مراجع الجداول القديمة.

### DB-005 — ازدواج محرك السندات

يوجد محركان:

- الحالي: `financial_voucher_headers` و`financial_voucher_details`.
- القديم: `voucher_headers` و`voucher_details`.

الكود الحالي يستخدم المحرك الأول. الجداول القديمة فارغة في النسخة المرفوعة، لكنها مرتبطة بجداول قديمة أخرى.

**الحل:** الإبقاء عليها كـ Legacy وعدم استخدامها في أي تطوير جديد، ثم عزلها في حزمة تنظيف لاحقة بعد فحص بيئة التشغيل.

### DB-006 — ازدواج جداول أسعار الصرف

يوجد:

- `exchange_rates`: الجدول الحالي المستخدم في المرحلة الأولى.
- `currency_exchange_rates`: جدول قديم بمعرفات نصية.

**الحل:** اعتماد `exchange_rates` فقط في الكود الجديد، وتصنيف الآخر Legacy.

### DB-007 — قيد كود العملة عالمي بدلاً من داخل الشركة

جدول `currencies` يحتوي فهرساً فريداً على `Currency_Code` فقط، بينما جميع خدمات العملات تعمل حسب الشركة.

**الأثر:** لا يمكن لشركتين مختلفتين تعريف `YER` أو `SAR` كلٌ ضمن بياناتها.

لا يمكن إزالة هذا القيد فوراً لأن جداول Legacy تربط `Currency_Code` وحده كمفتاح خارجي.

**الحل:** فك روابط Legacy أو تحويلها إلى ربط `Currency_ID`، ثم اعتماد فهرس:

`Company_ID + Currency_Code`

### DB-008 — أطوال معرف الشركة غير موحدة

- `companies.Company_ID`: `VARCHAR(50)`.
- بعض الجداول الحالية: `VARCHAR(50)`.
- جداول قديمة مثل `chart_of_accounts` و`cost_centers` و`projects`: `VARCHAR(36)`.

**الأثر:** يمنع أو يعقد المفاتيح الخارجية ويزيد احتمالات القص إذا تغير نمط معرف الشركة.

**الحل المستهدف:** توحيد جميع `Company_ID` إلى `VARCHAR(50)` مع نفس Collation ثم إضافة المفاتيح الخارجية بعد فحص القيم اليتيمة.

### DB-009 — سجل EF غير ممثل للبنية الحقيقية

`__EFMigrationsHistory` يحتوي ترقية واحدة فقط، بينما القاعدة تحتوي عشرات الجداول والترقيات اليدوية.

**الأثر:** لا يمكن الاعتماد على `Database.Migrate()` وحده لمعرفة حالة القاعدة، وقد يحاول EF تنفيذ تغييرات سبق تنفيذها يدوياً.

**الحل:** إنشاء Baseline رسمي للبنية الحالية، ثم تسجيل الترقيات المستقبلية في جدول ترقيات موحد أو ضمن EF Migrations فقط.

### DB-010 — غياب Triggers من النسخة الاحتياطية

ملف النسخة المرفوعة لا يحتوي تعريفات `CREATE TRIGGER`، لذلك لا يمكن اعتباره نسخة كاملة من قواعد الحماية الخادمية حتى لو كانت الـTriggers موجودة في السيرفر.

**الحل:** تفعيل خيار تصدير Triggers في النسخ الاحتياطية القادمة، وإعادة إنشاء Triggers المعتمدة بواسطة ملفات ترقية مسجلة.

## 3. نقاط مطابقة جيدة

- جداول `payment_requests` وتفاصيلها ومرفقاتها مطابقة في هيكلها العام لإعدادات `AppDbContext`.
- جداول السندات الحالية تحتوي حقول المراجعة والاعتماد والترحيل والتدقيق.
- جداول القيود المحاسبية موجودة وتحتوي علاقة رأس/تفاصيل.
- `tenant_branches` هو الجدول الصحيح المستخدم حالياً للفروع.
- جداول `system_settings` و`fiscal_periods` و`exchange_rates` موجودة وفق حزمة المرحلة الأولى.
- دليل الحسابات يملك مفتاحاً فريداً حسب الشركة والكود.

## 4. خطة الإصلاح المعتمدة

### المرحلة A — إصلاحات آمنة وفورية

- عزل `bank_accounts` القديم إذا كان فارغاً وإنشاء الجدول المطابق للكود.
- تصحيح فهرس أرقام السندات ليصبح حسب الفرع والسنة والنوع.
- إضافة فحوص تشخيصية للقيم اليتيمة والتعارضات.
- عدم حذف أي جدول أو بيانات.

### المرحلة B — توحيد المعرفات والعلاقات

- تحويل `Branch_ID` في السندات والقيود إلى `INT` مع تعديل الكود.
- توحيد `Company_ID` إلى `VARCHAR(50)`.
- إضافة مفاتيح خارجية للشركة والفرع والسنة والحساب بعد معالجة القيم اليتيمة.

### المرحلة C — إغلاق الجداول القديمة

- عزل `branches` و`voucher_headers` و`voucher_details` و`currency_exchange_rates`.
- التأكد من عدم وجود كود أو تقارير تستخدمها.
- لا حذف إلا بقرار مستقل وبعد نسخة احتياطية واختبار استعادة.

### المرحلة D — Baseline وترقيات آلية

- إنشاء Baseline رسمي للقاعدة الحالية.
- منع ملفات SQL غير المسجلة مستقبلاً.
- إضافة جدول سجل تنفيذ لكل حزمة SQL أو توحيد الترقيات داخل EF.

## 5. قرار السلامة

لا تعتبر قاعدة البيانات جاهزة للإغلاق النهائي قبل تنفيذ المراحل A وB والتحقق من بناء API واختبار الدخول والسندات ودليل الحسابات والعملات والبنوك والفروع.

كل إصلاح يجب أن يكون:

- آمناً لإعادة التشغيل.
- بلا حذف بيانات.
- مسبوقاً بفحوص وجود الأعمدة والفهارس والجداول.
- متبوعاً باستعلام تحقق واضح.
