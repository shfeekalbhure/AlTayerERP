# قبول الجزء 31 — السندات وطلب الصرف

## نطاق هذه الجولة
- الفرع: `agent/mobile-payment-request-completion`.
- كود الترقيم المعتمد: `PAYMENT_REQUEST`.
- يمنع تنفيذ أي SQL أو تعديل قاعدة البيانات.
- لا يبدأ UAT إلا بعد نجاح API وDesktop وMobile Android على Commit الإصلاح نفسه.

## أكواد الصلاحيات الفعلية
- إنشاء/تعديل/إرسال الطلب: `PaymentRequest.Add` و`PaymentRequest.Edit`.
- المراجعة: `PaymentRequest.Approve`؛ لا توجد صلاحية Review مستقلة في البنية الحالية.
- الاعتماد: `PaymentRequest.Approve` مع فصل خادمي بين المراجع والمعتمد.
- الإرجاع والرفض: `PaymentRequest.Unapprove`.
- إنشاء سند الصرف: `PaymentVoucher.Add`.

## حسابات UAT
- U1: منشئ فقط.
- U2: مراجع فقط.
- U3: معتمد فقط.
- U4: مخول بإنشاء سند الصرف عبر `PaymentVoucher.Add`.
- U5: مستخدم سلبي.
- U6: مراجع ومعتمد معاً لاختبار المنع الخادمي.

## قواعد الحالة النهائية
| الحالة الحالية | الإجراء | الحالة الجديدة | الصلاحية | فصل الواجبات |
|---|---|---|---|---|
| `DRAFT` أو `RETURNED` | تعديل/إرسال | `DRAFT` أو `PENDING_REVIEW` | `PaymentRequest.Edit` | المنشئ فقط |
| `PENDING_REVIEW` | مراجعة | `PENDING_APPROVAL` | `PaymentRequest.Approve` | ليس المنشئ |
| `PENDING_REVIEW` | إرجاع | `RETURNED` | `PaymentRequest.Unapprove` | ليس المنشئ |
| `PENDING_APPROVAL` | اعتماد | `APPROVED` | `PaymentRequest.Approve` | ليس المنشئ ولا أحدث مراجع |
| `PENDING_APPROVAL` | رفض/إرجاع | `REJECTED` أو `RETURNED` | `PaymentRequest.Unapprove` | ليس المنشئ |
| `APPROVED` | إنشاء سند صرف | تبقى `APPROVED` | `PaymentVoucher.Add` | ليس المنشئ |

## SOD-01 — فصل المراجع عن المعتمد

### SOD-01-A — منشئ ≠ مراجع ≠ معتمد
1. ينشئ U1 الطلب ويرسله.
2. يراجعه U2 لينتقل إلى `PENDING_APPROVAL`.
3. يعتمد U3 الطلب.

**المتوقع:** نجاح الاعتماد، وآخر سجل `REVIEW` للمستند يحمل U2، وسجل `APPROVE` يحمل U3.

### SOD-01-B — المراجع = المعتمد
1. يراجع U6 الطلب.
2. يحاول U6 اعتماد الطلب نفسه.

**المتوقع:** HTTP 409 بالنص: «لا يسمح للمستخدم الذي راجع طلب الصرف باعتماده. يجب أن ينفذ الاعتماد مستخدم آخر مخول.» ولا ينشأ سجل `APPROVE` ناجح، مع تسجيل `APPROVE_BLOCKED_SAME_REVIEWER`.

### SOD-01-C — لا يوجد REVIEW صالح
1. جهز طلباً في `PENDING_APPROVAL` دون سجل `REVIEW` مطابق في `audit_logs` ضمن بيئة اختبار معزولة.
2. حاول الاعتماد بواسطة U3.

**المتوقع:** HTTP 409 برسالة عدم وجود مراجعة ناجحة موثقة، وتسجيل `APPROVE_BLOCKED_NO_REVIEW`.

### SOD-01-D — مراجعة قديمة ثم دورة جديدة
1. يراجع U2 الطلب.
2. يعيده U3 من مرحلة الاعتماد.
3. يعدله U1 ويعيد إرساله.
4. يراجعه U6.
5. يحاول U2 الاعتماد ثم يحاول U6 الاعتماد.

**المتوقع:** المقارنة تكون مع أحدث `REVIEW` فقط: يسمح لـU2 إذا كان مخولاً، ويمنع U6.

## CONC-01 — التزامن باستخدام Created_At/Updated_At

### تعريف الدقة المعتمد
- Entity: `DateTime` و`DateTime?` دون نوع عمود صريح.
- Fluent API: لا يوجد تخصيص دقة لهذه الحقول.
- سكربت الحزمة: `Created_At DATETIME` و`Updated_At DATETIME` دون `(3)` أو `(6)`.
- المحافظة المطبقة: UTC ودقة الثانية، لأنها الدقة المؤكدة من ملف SQL دون تغيير المخطط.
- بعد الحفظ يعيد API قراءة السجل من قاعدة البيانات قبل إرساله للجوال.
- الجوال يطبع القيمة إلى UTC ودقة الثانية قبل إعادتها إلى API.
- `System.Text.Json` ينقل `DateTimeKind.Utc` بصيغة ISO 8601 Round-trip مع `Z`.

### CONC-01-A — خمس عمليات حفظ متتالية
1. افتح المسودة واحفظها خمس مرات متتالية دون تعديل خارجي.
2. أعد فتحها بين كل عملية.

**المتوقع:** لا يظهر 409 وهمي.

### CONC-01-B — تعارض حقيقي
1. افتح المسودة في جلستين A وB.
2. احفظ A.
3. احفظ B دون تحديث.

**المتوقع:** A تنجح وB تحصل على HTTP 409 برسالة التعديل بواسطة مستخدم آخر.

### CONC-01-C — إعادة تشغيل API
1. افتح المسودة وسجل آخر توقيت.
2. أعد تشغيل API.
3. افتح المسودة ثم احفظ تعديلاً مشروعاً.

**المتوقع:** لا 409 وهمي بسبب DateTimeKind أو المنطقة الزمنية.

### CONC-01-D — MySQL → API → Mobile → API
1. سجل القيمة الفعلية المخزنة.
2. قارنها بالقيمة في JSON وبالقيمة التي يعيدها الجوال.

**المتوقع:** القيم بعد التطبيع متساوية على UTC ودقة الثانية.

## بقية اختبارات القبول الإلزامية
1. تحميل الحسابات ومراكز التكلفة والعملات وطرق السداد.
2. إنشاء مسودة وحفظها.
3. إعادة فتح المسودة واسترجاع `Reference_No`.
4. تعديل المسودة.
5. العملة المحلية بسعر 1 والأجنبي صفر.
6. العملة الأجنبية: المحلي = الأجنبي × السعر.
7. عدة أسطر وإجمالي صحيح.
8. المرفقات: رفع وفتح وتنزيل وحذف حسب الحالة والصلاحية.
9. إرسال للمراجعة ومنع المنشئ من المراجعة.
10. الإرجاع من المراجعة وإعادة الإرسال.
11. الاعتماد والرفض والإرجاع من مرحلة الاعتماد.
12. السقف المالي ضمن الحد وتجاوزه وتغيره قبل السند.
13. منع من لا يملك `PaymentVoucher.Add`.
14. إنشاء سند واحد وربط `Payment_Voucher_ID` ومنع الثاني.
15. فتح السند المرتبط والقيد والطباعة إن توفرت.
16. 401 يعيد للدخول، 403 يمنع دون خروج، 409 يحدث الحالة.
17. عزل الشركة والفرع والسنة.
18. فحص التدقيق وعدم كشف Stack Trace أو SQL أو Tokens.
19. اختبار عدم الانحدار لسند القبض وسند الصرف.
