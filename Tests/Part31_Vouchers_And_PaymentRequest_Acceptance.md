# قبول الجزء 31 — السندات وطلب الصرف

## نطاق هذه الجولة
- الفرع: `agent/mobile-payment-request-completion`.
- كود الترقيم المعتمد في الكود: `PAYMENT_REQUEST`.
- يمنع تنفيذ أي SQL أو تعديل قاعدة البيانات في هذه الجولة.
- لا يبدأ UAT إلا بعد نجاح API وDesktop وMobile Android على Commit التعديلات الوظيفية نفسه.

## طلب الصرف — قواعد الحالة النهائية

| الحالة الحالية | الإجراء | الحالة الجديدة | الصلاحية الخادمية | السبب | فصل الواجبات |
|---|---|---|---|---|---|
| `DRAFT` أو `RETURNED` | تعديل | `DRAFT` | `PaymentRequest.Edit` | غير مطلوب | المنشئ فقط |
| `DRAFT` أو `RETURNED` | إرسال | `PENDING_REVIEW` | `PaymentRequest.Edit` | غير مطلوب | المنشئ فقط |
| `PENDING_REVIEW` | مراجعة | `PENDING_APPROVAL` | `PaymentRequest.Approve` | إلزامي | لا ينفذها المنشئ |
| `PENDING_REVIEW` | إرجاع | `RETURNED` | `PaymentRequest.Unapprove` | إلزامي | لا ينفذها المنشئ |
| `PENDING_APPROVAL` | اعتماد | `APPROVED` | `PaymentRequest.Approve` | إلزامي | لا ينفذها المنشئ |
| `PENDING_APPROVAL` | رفض | `REJECTED` | `PaymentRequest.Unapprove` | إلزامي | لا ينفذها المنشئ |
| `PENDING_APPROVAL` | إرجاع | `RETURNED` | `PaymentRequest.Unapprove` | إلزامي | لا ينفذها المنشئ |
| `APPROVED` | إنشاء سند صرف | تبقى `APPROVED` مع ربط السند | `PaymentVoucher.Add` | غير مطلوب | لا ينفذها المنشئ |
| `REJECTED` | إنشاء سند صرف | ممنوع | `PaymentVoucher.Add` | — | ممنوع دائماً |

## حالات القبول الإلزامية

### PR-01 — الترقيم
1. لا يُنفذ سكربت SQL حالياً.
2. تحقق برمجياً أن API يستدعي `NumberGeneratorService` بالكود `PAYMENT_REQUEST`.
3. بعد السماح باختبار قاعدة منفصلة لاحقاً، تحقق أن الإعداد النشط يحمل الاسم نفسه.

**النتيجة المتوقعة:** لا يوجد استخدام وظيفي لـ`REQUEST_PAYMENT` في API أو الجوال.

### PR-02 — حفظ المسودة ومرجع السطر
1. اختر مستفيداً وطريقة سداد وتاريخاً داخل فترة مفتوحة.
2. أضف سطراً محلياً مع `Reference_No` اختيارياً.
3. احفظ المسودة ثم أعد فتحها.
4. تحقق أن مرجع السطر عاد كما حُفظ.

**النتيجة المتوقعة:** تحفظ قيمة `Reference_No` وتظهر عند إعادة فتح المسودة.

### PR-03 — العملة المحلية والأجنبية
1. أضف سطراً بعملة محلية: الأجنبي صفر وسعر الصرف 1.
2. أضف سطراً بعملة أجنبية: المحلي = الأجنبي × السعر.
3. جرّب قيمة غير متطابقة.

**النتيجة المتوقعة:** يقبل السطرين الصحيحين ويرفض عدم التطابق برسالة عربية واضحة.

### PR-04 — التعديل المتزامن باستخدام الأعمدة الحالية
1. افتح المسودة على جهازين أو جلستين.
2. احفظ التعديل من الجلسة الأولى.
3. حاول الحفظ من الجلسة الثانية دون تحديث البيانات.

**النتيجة المتوقعة:** يعيد API الحالة 409 والرسالة: «تم تعديل طلب الصرف بواسطة مستخدم آخر. حدّث البيانات ثم أعد المحاولة.» باستخدام `Updated_At` أو `Created_At` الموجودين فعلياً، دون عمود جديد.

### PR-05 — فصل الواجبات
1. أنشئ طلباً بالمستخدم A.
2. حاول بالمستخدم A مراجعته واعتماده ورفضه وإرجاعه وإنشاء سند الصرف.
3. نفذ العمليات نفسها بمستخدمين مخولين مختلفين.

**النتيجة المتوقعة:** يمنع الخادم المستخدم A من العمليات الحساسة حتى لو ظهرت الأزرار، ويسمح للمستخدم المخول بحسب المرحلة والصلاحية.

### PR-06 — الإرجاع من مرحلة المراجعة
1. أرسل الطلب إلى `PENDING_REVIEW`.
2. أعده بسبب إلزامي.

**النتيجة المتوقعة:** ينتقل إلى `RETURNED` ويسجل `RETURN_FROM_REVIEW` مع المستخدم والوقت والسبب والحالة السابقة والجديدة.

### PR-07 — الإرجاع من مرحلة الاعتماد
1. راجع الطلب ليصل إلى `PENDING_APPROVAL`.
2. أعده بسبب إلزامي.

**النتيجة المتوقعة:** ينتقل إلى `RETURNED` ويسجل `RETURN_FROM_APPROVAL` مع جميع بيانات التدقيق.

### PR-08 — المراجعة والرفض والاعتماد
1. راجع الطلب بسبب.
2. اختبر الرفض من `PENDING_APPROVAL` بسبب.
3. أنشئ طلباً آخر وراجعه ثم اعتمده بسبب.

**النتيجة المتوقعة:** الرفض لا يعمل من `PENDING_REVIEW`، والاعتماد لا يعمل إلا من `PENDING_APPROVAL`، وجميع الانتقالات مدققة.

### PR-09 — السقف المالي
1. اعتمد طلباً داخل السقف.
2. اختبر طلباً يتجاوز الرصيد المتاح.
3. غيّر الرصيد المتاح قبل إنشاء السند ثم حاول الإنشاء.

**النتيجة المتوقعة:** يتحقق الخادم عند الاعتماد وعند إنشاء السند، ويرفض التجاوز بالحالة 409.

### PR-10 — صلاحية إنشاء سند الصرف
1. استخدم مستخدماً لديه `PaymentRequest.Add` ولا يملك `PaymentVoucher.Add`.
2. حاول إنشاء السند.
3. استخدم مستخدماً يملك `PaymentVoucher.Add` وليس منشئ الطلب.

**النتيجة المتوقعة:** الأولى 403، والثانية تنجح إذا بقيت الشروط الأخرى صحيحة.

### PR-11 — سند صرف واحد فقط
1. أنشئ سند الصرف من طلب معتمد.
2. تحقق من حفظ `Payment_Voucher_ID`.
3. كرر الطلب نفسه أو أرسل طلبين متزامنين.

**النتيجة المتوقعة:** ينشأ سند واحد فقط داخل Transaction واحدة، والمحاولة الثانية 409، ولا تتكرر حركة السقف أو التدقيق.

### PR-12 — فتح السند المرتبط
1. افتح الطلب بعد إنشاء السند.
2. اضغط رابط السند.

**النتيجة المتوقعة:** تفتح `PaymentVoucherDetailsPage` بالسند المرتبط نفسه.

### PR-13 — المرفقات
1. في `DRAFT` ارفع ملفاً أقل من 20MB ونزله وافتحه.
2. احذفه بسبب.
3. أرسل الطلب وحاول الإضافة أو الحذف.

**النتيجة المتوقعة:** التعديل على المرفقات في `DRAFT` أو `RETURNED` فقط، وبعد الإرسال يعيد الخادم 409، مع سجلي UPLOAD وDELETE.

### PR-14 — 401 و403 و409
1. استخدم رمز جلسة منتهياً.
2. استخدم مستخدماً بلا صلاحية.
3. نفذ تعارض تعديل أو إنشاء سند مكرر.

**النتيجة المتوقعة:**
- 401: تنظيف الجلسة والعودة إلى شاشة الدخول برسالة انتهاء الجلسة.
- 403: عرض رسالة منع الصلاحية دون تسجيل خروج.
- 409: عرض رسالة التعارض وإعادة تحميل حالة الطلب.
- لا يظهر Stack Trace أو تفاصيل MySQL للمستخدم.

### PR-15 — عزل الشركة والفرع والسنة
1. اطلب معرف طلب تابع لشركة أو فرع أو سنة أخرى.
2. عدل القيم المرسلة من العميل يدوياً.

**النتيجة المتوقعة:** لا يظهر السجل ولا يعدل؛ جميع الاستعلامات تعتمد سياق الجلسة الخادمي.

## أدلة القبول المطلوبة

- نجاح Build API وBuild Desktop وBuild Mobile Android.
- صور أو فيديو لكل انتقال رئيسي.
- استجابات 401 و403 و409.
- سجلات التدقيق للإنشاء والتعديل والإرسال والمراجعة والإرجاع والرفض والاعتماد وإنشاء السند والمرفقات.
- إثبات أن أي SQL لم يُنفذ وأن `master` لم يُدمج.
